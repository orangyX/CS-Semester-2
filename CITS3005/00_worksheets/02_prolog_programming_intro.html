Prolog programming

Writing knowledge bases · unification · lists · recursion · negation as failure

Write the programs, don't read them. The Lecture 3 sheet asked you to explain Prolog; this one asks you to produce it. Sets are labelled P1–P8 so nothing collides with the other sheets.

  1. P1–P2 are the basics: knowledge bases you write from a description, and unification predicted by hand.
  2. P3–P5 are the standard machinery — lists, recursion over a graph, arithmetic on successor terms.
  3. P6–P8 are where knowledge representation actually bites: negation as failure, a full knowledge base, and debugging.

Every program and every transcript in the answers was run in SWI-Prolog before being written down, including the ones that misbehave — where an answer says a query loops or returns something surprising, that is observed, not predicted. Run them yourself anyway: swipl kb.pl, then trace. when something is not doing what you expect.

P1 · Facts, rules, queries

Slides 23–25. Build a knowledge base from a description, then define relations over it.

P1.1 John and Susan have two children, Mary and Tom. Mary and Bob have a child, Alice. Write the facts, then define father/2 and mother/2.

▶Check
parent(john, mary).    parent(john, tom).
parent(susan, mary).   parent(susan, tom).
parent(mary, alice).   parent(bob, alice).

male(john).    male(tom).    male(bob).
female(susan). female(mary). female(alice).

father(X, Y) :- parent(X, Y), male(X).
mother(X, Y) :- parent(X, Y), female(X).

P1.2 Define sibling/2. Write the obvious version first, then query ?- sibling(mary, X). and fix what you find.

▶Check

The obvious version:

sibling(X, Y) :- parent(P, X), parent(P, Y).

It makes everyone their own sibling, since X and Y can bind to the same person. Add the inequality:

sibling(X, Y) :- parent(P, X), parent(P, Y), X \= Y.

Now a second problem shows up. Actual output:

?- findall(X-Y, sibling(X,Y), L).
L = [mary-tom, tom-mary, mary-tom, tom-mary].

Each pair appears twice — once via John, once via Susan. Prolog is not returning wrong answers; it is returning one solution per proof, and there are two proofs. That is what a resolution engine does.

Duplicate solutions are a fact of life in Prolog, not a bug to be stamped out. If you need them gone, wrap the query — setof/3 deduplicates and sorts — rather than contorting the rule. Contorting the rule usually means adding a cut, and a cut changes what the program means, not just what it prints.

P1.3 Define grandparent/2 and aunt_uncle/2, reusing what you already have.

▶Check
grandparent(X, Z) :- parent(X, Y), parent(Y, Z).

aunt_uncle(X, Y) :- sibling(X, P), parent(P, Y).
?- findall(X, aunt_uncle(X, alice), L).
L = [tom, tom].

Tom twice, inheriting the duplication from sibling/2 — the reason to notice it in P1.2.

Build relations out of relations. aunt_uncle/2 never mentions parent twice or male at all; it is defined against sibling/2, so improving sibling/2 improves it too. That layering is what a knowledge base is — the alternative is restating the same conditions in twelve places and having eleven of them go stale.

P1.4 Define ancestor/2. What are the two clauses, and does their order matter?

▶Check
ancestor(X, Y) :- parent(X, Y).
ancestor(X, Z) :- parent(X, Y), ancestor(Y, Z).
?- findall(X, ancestor(X, alice), L).
L = [mary, bob, john, susan].

Base case first, recursive case second. Declaratively the order is irrelevant — a program is a set of clauses. Operationally it decides the order solutions come back in, and it can decide whether the program terminates at all: see P8.1, where putting the recursive clause first turns this exact predicate into an infinite loop.

Note the recursive call is on ancestor(Y, Z), with parent(X, Y) first. Each step consumes one parent fact, so the recursion is guaranteed to shrink. That is the property to check every time you write a recursive rule: something must get smaller.

P1.5 father(X,Y) :- parent(X,Y), male(X). versus father(X,Y) :- male(X), parent(X,Y). — same answers? Same work?

▶Check

Same answers, different work. Both are the conjunction parent(X,Y) ∧ male(X), and conjunction commutes, so the set of solutions is identical.

Operationally they differ. The first generates parent pairs and filters by sex; the second generates males and then looks up their children. With many parents and few males, the second does less work; with the reverse, the first does.

The general heuristic: put the most constraining goal first. If one goal has a bound argument and another does not, the bound one narrows the search immediately and the unbound one enumerates. Ordering is the main tuning knob you have in Prolog — and it is one more place where the declarative reading and the operational behaviour come apart.

P2 · Unification

Slides 26–29, 33. The one operation everything else is built on. Predict each of these before running it.

P2.1 For each pair, say whether the two terms unify and give the bindings.

f(X, b)          =  f(a, Y)
f(X, X)          =  f(a, b)
p(X)             =  q(X)
f(a, X)          =  f(Y, g(Y))
[H|T]            =  [1, 2, 3]
[X|Y]            =  [1]
date(D, M, 2026) =  date(11, 8, Y)
foo              =  Foo

▶Check
termsresult
f(X,b) = f(a,Y)unifies — X = a, Y = b
f(X,X) = f(a,b)fails — X cannot be both a and b
p(X) = q(X)fails — different functors, checked before arguments
f(a,X) = f(Y,g(Y))unifies — Y = a, then X = g(a). Bindings propagate.
[H|T] = [1,2,3]unifies — H = 1, T = [2,3]
[X|Y] = [1]unifies — X = 1, Y = []. A one-element list is head 1, tail empty.
date(D,M,2026) = date(11,8,Y)unifies — D = 11, M = 8, Y = 2026. Information flows both ways.
foo = Foounifies — Foo is a variable (capital initial); it binds to the atom foo

The algorithm, in one line: same functor and arity, then recursively unify arguments left to right, with a variable absorbing whatever sits opposite it — and once bound it stays bound for the rest of the match. Row four is the one people get wrong: by the time X is matched, Y is already a.

Row three is worth its own note: unification is structural, not semantic. It never asks what p and q mean.

P2.2 What does ?- X = f(X). do? Should it succeed?

▶Check
?- X = f(X).
X = f(X).                            % succeeds — a cyclic term

?- unify_with_occurs_check(Y, f(Y)).
false.

Logically it should fail. No finite term is a proper subterm of itself, so there is no substitution making both sides equal. Checking for this is the occurs check.

SWI-Prolog omits it by default and builds a cyclic term instead, because the check costs time on every single unification and the situation almost never arises in real programs. Use unify_with_occurs_check/2 when you need the logically correct behaviour.

This is a gap between Prolog and the logic, like the ones in the Lecture 3 sheet. Standard resolution is defined with the occurs check; the default implementation is unsound without it. Worth knowing exists, not worth worrying about weekly — but it is exactly the kind of thing a knowledge representation exam likes to ask, because it shows whether you know the difference between a proof procedure and its implementation.

P2.3 Predict both: ?- X = 1+2. and ?- X is 1+2.. Then explain why ?- 3 = 1+2. fails.

▶Check
?- X = 1+2.
X = 1+2.

?- X is 1+2.
X = 3.

?- 3 = 1+2.
false.

= is unification, and 1+2 is just the compound term +(1,2) — slide 28's point that functions are not evaluated. So X binds to the expression itself.

is/2 is arithmetic evaluation: it evaluates its right side as an arithmetic expression and unifies the result with the left. It is one of the non-logical operators — it fails or errors if the right side has unbound variables, so it works in one direction only.

3 = 1+2 fails because an integer and a compound term have different shapes. Nothing is being computed for them to agree about. Structure, not value.

P2.4 What kind of term is [a, b, c] really? Show it has the same status as date(11, 8, 2026).

▶Check
?- X = [a,b,c], X = [H|T].
X = [a,b,c], H = a, T = [b,c].

?- [a,b,c] =.. L.
L = ['[|]', a, [b,c]].

A list is a compound term like any other — slide 28 lists it as a special case. [a,b,c] is a two-argument term (head and tail) whose functor SWI writes as '[|]', nested three deep and ending in the atom []:

'[|]'(a, '[|]'(b, '[|]'(c, [])))

The bracket notation is sugar. Everything about lists — member, append, all of P3 — is just unification against that nested structure, which is why the definitions are so short.

=.. ("univ") takes any term apart into functor and arguments, and is worth knowing for exactly this kind of check.

P2.5 You load a program and SWI warns: Singleton variables: [L]. What does that mean, and when is it a real bug?

▶Check

A variable occurring once in a clause. Since a variable only does work by appearing twice — once to be bound, once to be used — a single occurrence is usually either a typo or a variable you meant to ignore.

nearby(X, Y) :- connected(X, Y, L).     % warns: singleton L
nearby(X, Y) :- connected(X, Y, _).     % no warning, no documentation
nearby(X, Y) :- connected(X, Y, _L).    % no warning, still says "line"

The real bug it catches is a misspelling. Write connected(X, Y, Line) in one goal and Lien in the next and the clause silently stops working — both are now singletons, and the warning is the only sign.

The leading-underscore form is what the lecture uses in the transport knowledge base, and it is the right habit: it silences the warning while keeping the name for whoever reads the clause next.

P3 · Lists

Slide 28 mentions lists as a special case of compound terms. Here is what you actually do with them.

P3.1 Write mem/2 — true when the first argument is an element of the second. Two clauses, no arithmetic.

▶Check
mem(X, [X|_]).
mem(X, [_|T]) :- mem(X, T).
?- findall(X, mem(X, [a,b,c]), L).
L = [a, b, c].

Read the clauses as knowledge, not as a loop: X is a member if it is the head; or if it is a member of the tail. The base case is the first clause — no arithmetic, no index, no counter.

Because the first argument may be unbound, the same predicate generates members as well as testing them. One definition, two modes, for free. That is the payoff of relations over functions.

P3.2 Write app/3 (append). Then predict ?- app(X, Y, [1,2]). — this is the one to think about.

▶Check
app([], L, L).
app([H|T], L, [H|R]) :- app(T, L, R).
?- findall(X-Y, app(X, Y, [1,2]), L).
L = [[]-[1,2], [1]-[2], [1,2]-[]].

Every way of splitting the list. You wrote a predicate for joining two lists and got list-splitting at no extra cost, because app/3 is a relation among three lists rather than a function of two.

The recursive clause is worth reading slowly: it says the head of the first list is also the head of the result, and the rest follows by recursion. There is no code that "copies" anything — the copying is unification building the answer term.

This reversibility is the thing Prolog does that other languages do not, and it is why the unit cares. But it is not universal: len/2 below stops being reversible the moment you use is/2, because arithmetic evaluation only runs one way. Every non-logical operator you add costs you a mode.

P3.3 Write len/2. Why does this one need is/2, and what does it cost?

▶Check
len([], 0).
len([_|T], N) :- len(T, M), N is M+1.

You need is/2 because the length is a number to be computed, and Prolog does not evaluate terms (P2.3). Without it, len([a,b], N) would bind N to 0+1+1.

?- len(L, 3).
L = [_A, _B, _C] ;
% ... hangs — never returns from the search for a second solution

The cost is reversibility, and this is one to run rather than assume. Backwards you do get an answer — a list of three unbound variables — but asking for the next one never terminates: the recursion keeps generating longer and longer lists, and is/2 can only test each candidate rather than solve for the length. Compare P5.1, where the successor version terminates in both directions.

Note also that the recursive call comes before the arithmetic. It has to — M must be bound by the time N is M+1 runs, or is/2 raises an instantiation error.

A fully relational version uses successor terms instead of integers — which is exactly what P5 is about, and exactly why the lecture's arithmetic example is built that way.

P3.4 Write rev/2 twice: the naive version using app/3, and an accumulator version. What changes?

▶Check
% naive — quadratic
rev([], []).
rev([H|T], R) :- rev(T, S), app(S, [H], R).

% accumulator — linear
revacc(L, R) :- revacc(L, [], R).
revacc([], A, A).
revacc([H|T], A, R) :- revacc(T, [H|A], R).
?- rev([1,2,3], R).
R = [3, 2, 1].

?- revacc([1,2,3], R).
R = [3, 2, 1].

The naive version walks the whole accumulated list on every step to stick one element on the end, so an n-element list costs about n²/2 steps. The accumulator version pushes each element onto the front of a growing second list — front-insertion is one unification, back-insertion is a traversal — and finishes in n.

The accumulator idiom is worth having in your hands: a helper with one extra argument carrying the answer-so-far, and a base case that hands the accumulator back. It reappears in P4 as the visited-list, which is the same trick used for a different purpose.

P3.5 Write last_/2 (the last element) and nth/3 (the Nth element, counting from 1). Underscore in the name to avoid clashing with the built-ins.

▶Check
last_([X], X).
last_([_|T], X) :- last_(T, X).

nth(1, [X|_], X).
nth(N, [_|T], X) :- N > 1, M is N-1, nth(M, T, X).
?- last_([a,b,c], X).
X = c.

?- nth(2, [a,b,c], X).
X = b.

last_/2's base case is [X], not [] — the last element of an empty list does not exist, so there should be no clause for it. Failure is the right answer to a question with no answer, and adding a clause to "handle" it would be wrong.

nth/3's N > 1 guard is worth testing rather than assuming. Drop it and the answers do not change — nth(1, [a,b,c], X) still gives only X = a, because the second clause descends with N going negative and runs off the end of the list, failing. What the guard buys is mutually exclusive clauses: exactly one can apply, so no pointless descent happens and the predicate is deterministic.

The habit worth forming: check whether two clauses can both fire, and check it by running it. Overlapping clauses sometimes cost a spurious solution and sometimes only wasted work — P5.3 is a case where the cost is real — and guessing which is not reliable.

P4 · Recursion over a graph

Slides 31–32, extended. The transport knowledge base, made to do what you actually wanted.

The facts, for reference. Save these with your work — P4 and P6 both build on them.

connected(bond_street, oxford_circus, central).
connected(oxford_circus, tottenham_court_road, central).
connected(bond_street, green_park, jubilee).
connected(green_park, charing_cross, jubilee).
connected(green_park, piccadilly_circus, piccadilly).
connected(piccadilly_circus, leicester_square, piccadilly).
connected(green_park, oxford_circus, victoria).
connected(oxford_circus, piccadilly_circus, bakerloo).
connected(piccadilly_circus, charing_cross, bakerloo).
connected(tottenham_court_road, leicester_square, northern).
connected(leicester_square, charing_cross, northern).

Plus the lecture's two rules: nearby(X,Y) :- connected(X,Y,_L). and nearby(X,Y) :- connected(X,Z,L), connected(Z,Y,L).

P4.1 The lecture's connected/3 facts are directional. Write link/3 so travel works both ways, without editing any facts.

▶Check
link(X, Y, L) :- connected(X, Y, L).
link(X, Y, L) :- connected(Y, X, L).

Two clauses, and every fact now reads in both directions. Never edit facts to fix a rule. The facts record what the survey said; the rules record what you want to conclude from it. Duplicating eleven reversed facts would double the maintenance and guarantee they drift apart.

This is also the general shape for any symmetric closure of a stored relation, and the same idea covers reflexive and transitive closure — P4.2 does transitive.

P4.2 Write reachable/2 — any number of stops, any lines. Try the obvious version first and say what happens.

▶Check

The obvious version:

reachable(X, Y) :- link(X, Y, _).
reachable(X, Z) :- link(X, Y, _), reachable(Y, Z).

Because link/3 is symmetric the graph has cycles, so this walks Bond Street → Oxford Circus → Bond Street → … forever. Prolog's depth-first search never notices the repeat. It may find an answer first by luck; it will not terminate on a query with no answer.

Carry the stations already visited:

reachable(X, Y) :- reachable(X, Y, [X]).

reachable(X, Y, _) :- link(X, Y, _).
reachable(X, Y, V) :- link(X, Z, _), \+ mem(Z, V), reachable(Z, Y, [Z|V]).
?- reachable(bond_street, leicester_square).
true.

Same accumulator idiom as P3.4, doing a different job: the extra argument now rules moves out rather than building an answer. The two-clause wrapper hides it so callers still see reachable/2.

The declarative reading of the broken version is perfectly correct. "X reaches Z if X links to some Y that reaches Z" is true. It fails only because of how Prolog searches — depth first, no memory. That gap between what a program means and what it does is the recurring theme of this half of the unit, and it is why slide 42's "clear systematic way to apply resolution" is doing real work.

P4.3 Extend it to route/3, returning the actual list of stations travelled.

▶Check
route(X, Y, P) :- route(X, Y, [X], P).

route(X, Y, V, P) :- link(X, Y, _), revacc([Y|V], P).
route(X, Y, V, P) :- link(X, Z, _), Z \== Y, \+ mem(Z, V),
                     route(Z, Y, [Z|V], P).
?- route(bond_street, charing_cross, P).
P = [bond_street, oxford_circus, tottenham_court_road,
     leicester_square, charing_cross].

The visited list is already the path — in reverse, since each new station was pushed on the front. So the base case reverses it (P3.4) and hands it back. One accumulator, two jobs.

Z \== Y stops the recursive clause from stepping onto the destination and then looking for it again, which would produce longer duplicate routes.

P4.4 That first route has four hops, but Bond Street → Green Park → Charing Cross has two. Why did Prolog not find the short one first, and what would you do about it?

▶Check

Because search is depth-first, not breadth-first. At Bond Street the first matching fact is the Oxford Circus one, so Prolog commits to that branch and drives it all the way to a solution before ever trying Green Park. It returns the first route it completes, which has nothing to do with length.

?- findall(P, route(bond_street, leicester_square, P), L), length(L, N).
N = 17.

All seventeen routes are there, in depth-first order. So one fix is to collect them and pick:

shortest(X, Y, P) :-
    findall(L-Q, (route(X, Y, Q), len(Q, L)), All),
    sort(All, [_-P|_]).

This is a genuine limitation, not a mistake in your program. Prolog's strategy is fixed, so anything requiring a different search order has to be built on top — collect all solutions and sort, or carry a depth bound and iterate. It is the same lesson as P4.2 from the other side: the logic is fine, the search is what you have to manage.

P5 · Arithmetic on successor terms

Slide 36, taken apart and rebuilt. Numbers as structures, so everything stays relational.

P5.1 Using zero and f/1 as on slide 36, write add/3. Then try it backwards.

▶Check
add(zero, Y, Y).
add(f(X), Y, f(Z)) :- add(X, Y, Z).
?- add(f(zero), f(f(zero)), S).       % 1 + 2
S = f(f(f(zero))).                       % 3

?- findall(X-Y, add(X, Y, f(f(zero))), L).
L = [zero-f(f(zero)), f(zero)-f(zero), f(f(zero))-zero].

Two clauses and no arithmetic at all — the recursion peels one f off the first argument and adds one to the result. The structure does the counting.

And it runs backwards: asking for all pairs summing to 2 enumerates them, because nothing here is evaluated in a fixed direction. Compare len/2 in P3.3, which loses that the moment is/2 appears. This is the whole reason slide 36 uses successor terms rather than integers.

P5.2 Write mult/3, lt/2 (strictly less than) and sub/3.

▶Check
mult(zero, _, zero).
mult(f(X), Y, Z) :- mult(X, Y, W), add(Y, W, Z).

lt(zero, f(_)).
lt(f(X), f(Y)) :- lt(X, Y).

sub(X, zero, X).
sub(f(X), f(Y), Z) :- sub(X, Y, Z).
?- mult(f(f(zero)), f(f(f(zero))), Z).     % 2 * 3
Z = f(f(f(f(f(f(zero)))))).                  % 6

mult/3 is repeated addition, defined against add/3 — layering again.

lt/2's base case says zero is less than any successor, which is also what makes it false everywhere it should be: lt(zero, zero) matches no clause. sub/3 peels one from each side until the subtrahend runs out, so it simply fails when the answer would be negative — correct behaviour over the naturals, and you did not have to write a check for it.

P5.3 Slide 36's reduce/2 is claimed to do arithmetic modulo 3. Test it on 3 and on 6. Is it a normaliser?

▶Check
limit(f(f(f(zero)))).
reduce(zero, zero).
reduce(X, zero) :- limit(X).
reduce(f(X), f(Y)) :- reduce(X, Y).
?- findall(R, reduce(f(f(f(zero))), R), L).        % 3
L = [zero, f(f(f(zero)))].                          % 0, then 3

?- findall(R, reduce(f(f(f(f(f(f(zero)))))), R), L).  % 6
L = [f(f(f(zero))), f(f(f(f(f(f(zero))))))].          % 3, then 6 — never 0

No. Two things are wrong, and only the first is a matter of ordering.

  • It is non-deterministic. On 3, the second clause collapses to zero and the third peels instead, giving 3 back unreduced. The right answer comes first only because reduce(X,zero) :- limit(X) is written above the peeling clause. Swap them and the first solution changes.
  • It does not reduce far enough. On 6 it never produces 0 at all. The limit clause fires at most once per solution, so it removes one multiple of 3, not all of them — 6 becomes 3 and stops.

So the slide's program works for inputs up to about twice the modulus and quietly stops working after that. Worth raising in the workshop; slide 36 says the example is explored further there.

P5.4 Write a correct normaliser norm/2 — repeatedly subtract the modulus until what is left is below it.

▶Check
norm(X, X) :- limit(M), lt(X, M).
norm(X, R) :- limit(M), \+ lt(X, M), sub(X, M, Y), norm(Y, R).
?- norm(f(f(f(f(zero)))), R).             % 4
R = f(zero).                                % 1

?- norm(f(f(f(f(f(f(zero)))))), R).         % 6
R = zero.                                   % 0  — correct

Built from P5.2's lt/2 and sub/3. The two clauses are mutually exclusive by construction — one requires lt(X,M), the other its negation — so there is exactly one solution and no clause-order dependence. Contrast P5.3, where the two reduce clauses overlap.

That is the general repair for a non-deterministic predicate: make the clause guards exclusive, rather than relying on which clause you wrote first. The cut would also silence the extra solution, but it would hide the overlap rather than remove it.

P5.5 Slide 36's equals/2 fails on 3 versus 0, even though 3 ≡ 0 (mod 3). Write a version that does not.

▶Check
eq3(X, Y) :- norm(X, A), norm(Y, A).
?- eq3(f(f(f(zero))), zero).                 % 3 =:= 0
true.

?- eq3(f(f(f(zero))), f(zero)).              % 3 =:= 1
false.

Two things are equal modulo 3 exactly when they normalise to the same term — and writing A twice is how you say "the same" in Prolog. Unification does the comparison; there is no equality test to write.

The original failed because both its clauses required the two arguments to have matching top-level shape — both zero, or both f(…) — so f(f(f(zero))) against zero matched no clause head and failed before any reduction happened. Normalise first, compare after, and the problem disappears.

Note it also matters that norm/2 is deterministic. Built on the original reduce/2, this same one-line definition gets the right answer for 3 and the wrong one for 6.

P6 · Negation as failure

Slide 32's closed-world question, made operational. The single biggest gap between Prolog and the FOL semantics.

P6.1 What does \+ Goal mean, exactly? State it in terms of the proof, not the world.

▶Check

\+ Goal succeeds if Prolog fails to prove Goal, and fails if it proves it. That is all. It says nothing about truth or falsity in any domain — it is a statement about what this knowledge base can derive.

Two consequences that follow immediately:

  • It binds nothing. A successful \+ G leaves every variable in G exactly as it found them, since the only way it succeeds is by G failing, and failure undoes bindings.
  • It is not the ¬ of section 16. Definite clauses have no negative literals; \+ is a control construct bolted on, in the same family as the non-logical operators of slide 30.

P6.2 Predict ?- \+ nearby(X, Y). with both variables unbound. Then run it.

▶Check
?- \+ nearby(X, Y).
false.

It fails — and once you read \+ correctly that is obvious. It asks Prolog to prove nearby(X, Y); Prolog succeeds immediately with the first pair it finds; so the negation fails.

What it did not ask is "find me an X and Y that are not nearby." \+ cannot do that, because it never binds anything. Read aloud, \+ nearby(X,Y) with unbound variables means "no pair of stations anywhere is nearby" — which is false, and correctly reported as such.

This is called floundering, and it is the classic negation bug. The rule is: \+ is only meaningful on a ground goal — one with no unbound variables. Anything else is asking a question you did not mean. Bind first, negate second; P6.3 is what that looks like.

P6.3 Now write not_nearby/2 properly. You will need a way to enumerate stations.

▶Check
station(S) :- connected(S, _, _).
station(S) :- connected(_, S, _).

not_nearby(X, Y) :- station(X), station(Y), X \== Y, \+ nearby(X, Y).
?- not_nearby(bond_street, leicester_square).
true.

?- setof(X-Y, not_nearby(X,Y), L), length(L, N).
N = 26.

The generators come first. station(X), station(Y) bind both variables before \+ ever runs, so by the time the negation is reached the goal is ground and the question is the one you meant. This is the generate-and-test pattern, and with \+ the order is not a preference — it is correctness.

station/1 has two clauses because a station may appear in either argument position, and it will report duplicates. setof/3 above deduplicates; if you needed station/1 itself clean you would use setof inside it.

P6.4 Slide 32 asks why we can conclude two London stations are not nearby, but not that Subiaco and Leederville are not. Your not_nearby/2 returns 26 pairs. What are those 26 pairs actually evidence of?

▶Check

They are pairs Prolog could not prove nearby. Nothing more. Turning that into a claim about the world requires an extra assumption you supply from outside: that connected/3 records every connection there is — the closed-world assumption.

For this knowledge base that assumption is reasonable: the eleven facts are the whole map. Ask about Subiaco and the assumption is plainly false — the knowledge base has never heard of Perth, so failure records ignorance, not absence. Same query, same output, completely different epistemic status, and Prolog cannot tell them apart.

Note your station/1 guard is doing quiet work here: not_nearby(subiaco, leederville) fails rather than succeeding, because neither is a known station. That is a better answer than true — but only because you chose to require it.

This is the practical face of the open-world/closed-world distinction that runs through the rest of the unit. Section 16.5 of the Lecture 3 sheet has the contrast: a clausal program with two models leaves a proposition genuinely undecided, whereas Prolog reports false and gives you no way to tell "known false" from "not known". When you move to ontologies and description logics later, the semantics goes open-world by default, and this is the assumption being dropped.

P7 · A knowledge base end to end

Slide 12's university domain, built for real. Facts, derived relations, and a query that needs "for all".

P7.1 Write facts for four units, their prerequisites, and what two students have completed.

▶Check
unit(cits1001).  unit(cits2211).  unit(cits3005).  unit(cits3011).

prereq(cits1001, cits2211).      % cits1001 is a prereq of cits2211
prereq(cits2211, cits3005).
prereq(cits1001, cits3011).

completed(maria, cits1001).
completed(maria, cits2211).
completed(tom, cits1001).

Fix the argument order and write it down. prereq(P, U) reading "P is a prerequisite of U" is a choice; the reverse is equally defensible. Slide 12 does not settle it, and every rule you write afterwards depends on it. A comment on the first fact costs nothing and prevents the bug where half your rules read it one way.

P7.2 Write can_enrol/2: the student has completed every prerequisite of the unit. Prolog has no universal quantifier — how do you say "for all"?

▶Check
can_enrol(S, U) :- unit(U), \+ ( prereq(P, U), \+ completed(S, P) ).
?- can_enrol(maria, cits3005).
true.

?- can_enrol(tom, cits3005).
false.

?- can_enrol(maria, cits1001).
true.

Double negation is how you get "for all". "Every prerequisite is completed" becomes "there is no prerequisite that is not completed" — which is the quantifier equivalence ∀X.α ≡ ¬∃X.¬α from set D of the proof drill, written in the only vocabulary Prolog has.

The inner prereq(P, U) is the generator, and it runs inside the negation, so the floundering problem of P6.2 does not arise: P is bound by the time the inner \+ is reached. unit(U) is outside to make U ground first.

Note can_enrol(maria, cits1001) is true because cits1001 has no prerequisites, so there is trivially none uncompleted. The vacuous case falls out for free, which is exactly what you want and exactly what a hand-rolled counting version would get wrong.

P7.3 can_enrol/2 says no but not why. Write missing/3.

▶Check
missing(S, U, P) :- prereq(P, U), \+ completed(S, P).
?- findall(P, missing(tom, cits3005, P), L).
L = [cits2211].

The inside of the double negation, exposed as its own relation. The failing subgoal is the explanation — which is a nice property of writing knowledge bases this way, and one reason expert systems were built in Prolog: you can usually ask "why not" by naming the part that failed.

You could now define can_enrol(S,U) :- unit(U), \+ missing(S,U,_)., which reads better and behaves identically.

P7.4 Prerequisites chain: cits1001 → cits2211 → cits3005. Write all_prereq/2 for the transitive closure, then ready/2 requiring all of them.

▶Check
all_prereq(U, P) :- prereq(P, U).
all_prereq(U, P) :- prereq(Q, U), all_prereq(Q, P).

ready(S, U) :- unit(U), \+ ( all_prereq(U, P), \+ completed(S, P) ).
?- setof(P, all_prereq(cits3005, P), L).
L = [cits1001, cits2211].

?- ready(maria, cits3005).
true.

?- ready(tom, cits3005).
false.

Same closure shape as ancestor/2 in P1.4 and reachable/2 in P4.2 — base case, then one step plus recursion. It terminates here without a visited list because the prerequisite graph is acyclic and directed; add a cycle and it loops, exactly as P4.2 does.

ready/2 is can_enrol/2 with the transitive relation swapped in, and nothing else changed. That substitutability is the point of building in layers.

Worth asking whether ready/2 is the rule a university actually wants. Real prerequisites are usually satisfied by the immediate ones alone — you cannot have completed cits2211 without cits1001 anyway. The two rules agree on well-formed data and disagree on messy data, which is precisely when you find out which one you meant. Deciding that before writing the rule is knowledge representation; discovering it afterwards is debugging.

P8 · Debugging

Slides 33–35. Three programs that are wrong, and how you would find out.

P8.1 This is P1.4 with the clauses swapped. What happens, and why?

ancestor(X, Z) :- ancestor(X, Y), parent(Y, Z).
ancestor(X, Y) :- parent(X, Y).

▶Check
?- ancestor(john, alice).
ERROR: Stack limit (1.0Gb) exceeded
ERROR:   Stack depth: 6,340,655, ... Choice points: 6,340,649
ERROR:   Probable infinite recursion (cycle):

Left recursion. The first clause's leftmost goal is ancestor itself, with the same first argument. Prolog tries clauses top to bottom and goals left to right, so it calls ancestor(john, _), which calls ancestor(john, _), forever. It never reaches the base case, because the base case is written second and nothing ever backtracks that far.

The declarative reading is unchanged — the two clauses say exactly what they said before, and a set has no order. This is purely an artefact of depth-first, top-to-bottom search.

The rules that prevent it: base case first, and make sure the recursive goal is not the leftmost one with unchanged arguments. In P1.4, parent(X, Y) comes before the recursive call and consumes a fact each time, so the recursion is guaranteed to shrink.

P8.2 This loads with a warning and then quietly returns nothing. Find the bug.

nearby_line(X, Y, Line) :- connected(X, Y, Line).
nearby_line(X, Y, Line) :- connected(X, Z, Line), connected(Z, Y, Lien).

▶Check

Lien in the last goal — a typo for Line. SWI warns:

Warning: Singleton variables: [Lien]

The second clause is now wrong in two ways at once. The two legs no longer have to be on the same line, since Lien is a fresh variable unrelated to anything; and the Line returned in the head is only the first leg's line, so the answer is misleading rather than merely permissive.

The singleton warning is the whole diagnosis, and it is why you should never let warnings accumulate — a program with fifteen deliberate singletons has nowhere for the sixteenth, real one to show up. This is the concrete reason for the _L convention of P2.5.

Note also how the bug presents: no error, no crash, just fewer or stranger answers than you expected. In Prolog, wrong programs usually fail silently rather than complaining — which is why P8.3 matters.

P8.3 A query returns false and you are certain it should not. What do you actually do?

▶Check

Take the rule apart and run the goals one at a time at the prompt. A conjunction failing means some goal failed, and the fastest way to find which is to paste them in yourself:

?- station(bond_street).
true.
?- station(leicester_square).
true.
?- nearby(bond_street, leicester_square).
false.                              % so \+ nearby(...) succeeds — this is not the problem

Then, when the failure is not in one goal but in how they interact, use the trace and read the ports from P4 and slide 35 — Call, Exit, Fail, Redo:

?- trace, nearby(bond_street, charing_cross).
   Call: (12) nearby(bond_street, charing_cross) ? creep
   Call: (13) connected(bond_street, charing_cross, _10700) ? creep
   Fail: (13) connected(bond_street, charing_cross, _11590) ? creep
   Redo: (12) nearby(bond_street, charing_cross) ? creep
   ...
?- notrace.

The port to watch is the first unexpected Fail — everything above it worked, so the bug is at that goal or in what bound its arguments. Note the variable names change between Call and Fail; that is just Prolog renaming on backtracking, not a clue.

Two checks worth doing before reaching for the trace at all, because they catch most of it: read the warnings (P8.2), and check your argument order against the comment you wrote on the first fact (P7.1). Backwards prereq/2 produces exactly this symptom — a confident, silent false.

Do P6 and P7 if you do nothing else. Lists and recursion you will pick up from any Prolog tutorial; negation as failure and the closed-world assumption are what this unit is actually about, and P7.2's double negation is the idiom you will reach for constantly once you start writing real knowledge bases.

Run everything. P3.3, P5.3 and P8.1 are all cases where the program does something other than what it looks like it does — a list length that finds an answer and then never stops, a modular reduction that never reaches zero, two clauses that loop when swapped. None of those are visible by reading. Keep a scratch kb.pl open and paste as you go.
