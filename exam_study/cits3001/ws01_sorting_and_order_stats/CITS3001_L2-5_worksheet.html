Part A · Comparison sorts and the lower bound

5 questions · ~25 min

Lecture 2, slides 3–24. The one idea to hold onto: a comparison sort is a decision tree with $N!$ leaves, so its worst case is at least $\lg N!$, which is $\Theta(N \lg N)$. A5 is the one real proof in the lecture; A4 is where the exam turns it into numbers.

(b)

Swaps: $1 + 0 + 3 + 1 + 3 = 8$. Inversions in the original: (6,3), (6,2), (6,3), (3,2), (8,2), (8,7), (8,3), (7,3) — also 8.

They agree because each swap exchanges two adjacent out-of-order elements, which removes exactly one inversion and creates none. The sorted list has 0 inversions, so the number of swaps is exactly the starting inversion count. This is slide 11's point: an algorithm that removes one inversion at a time is $\Theta(N^2)$ in the worst case, because a reversed list has $N(N-1)/2$ inversions.

(c)

Every swap is preceded by one true comparison, and each inner loop that stops early adds one false comparison. Early stops happen at $l = 2, 4, 5$, so the count is $8 + 3 = 11$.

Check: per iteration, $1 + 1 + 3 + 2 + 4 = 11$ ✓. Note the stop at $l=5$: the new 3 meets the old 3, and 3 < 3 is false, so equal elements never pass each other. That is why insertion sort is stable.

(c)

The output is still sorted, but the sort is no longer stable. On a tie, < takes the right-hand element first, so an equal element from later in the original list jumps ahead of an earlier one. Taking from lhs on ties is exactly the tie-break by original position that defines stability.

A3prove

Cold, without the slides:

  1. Write pseudocode for merge(lhs, rhs) and merge_sort(xs).
  2. Give the time complexity with the argument the lecture uses, and the extra space used.
  3. State whether merge sort is optimal, in-place and stable, with a one-line reason for each.
(a) Pseudocode 
merge(lhs, rhs):
    result = []
    li, ri = 0, 0                  # smallest unused element of each list
    while li < len(lhs) and ri < len(rhs):
        if lhs[li] <= rhs[ri]:     # ties go left: keeps it stable
            append lhs[li]; li += 1
        else:
            append rhs[ri]; ri += 1
    append the leftovers lhs[li:] and rhs[ri:]
    return result

merge_sort(xs):
    if len(xs) <= 1: return xs     # trivially sorted
    mid = len(xs) // 2
    return merge(merge_sort(xs[:mid]), merge_sort(xs[mid:]))
(b) Complexity

Halving gives $O(\lg N)$ levels of recursion. At each level every element takes part in exactly one merge, and appending it costs $O(1)$, so each level costs $O(N)$. Total $O(N \lg N)$ in every case, since the splits never depend on the data. Equivalently, $T(N) = 2T(N/2) + O(N)$.

Extra space is $O(N)$ for the merge buffer, plus $O(\lg N)$ stack.

(c) Properties

Optimal: yes. $O(N \lg N)$ worst case meets the $\Omega(N \lg N)$ comparison lower bound (A5).

In-place: no. The merge needs an $O(N)$ buffer, far more than CLRS's "constant number of elements outside the list".

Stable: yes, because of the <=; see A2(c).

A4compute
  1. Why must the decision tree of a correct comparison sort on $N$ distinct elements have at least $N!$ leaves? What does the tree's height measure?
  2. Find the fewest comparisons that any comparison sort must make in the worst case for $N = 4$ and $N = 5$.
  3. Find the worst-case comparison counts of insertion sort and merge sort (lecture code) for $N = 4$ and $N = 5$.
  4. Merge sort's count for $N = 5$ exceeds your answer to (b). Does that contradict "merge sort is optimal"?
(a)

Each of the $N!$ input orderings needs a different permutation to sort it. If two orderings reached the same leaf, the algorithm would apply the same rearrangement to both and get one of them wrong. So there are at least $N!$ distinct leaves. The height is the longest root-to-leaf path, which is the number of comparisons in the worst case.

(b)

A binary tree of height $h$ has at most $2^h$ leaves, so $h \ge \lceil \lg N! \rceil$.

$N = 4$: $\lceil \lg 24 \rceil = 5$, since $2^4 = 16 \lt 24 \le 32$.

$N = 5$: $\lceil \lg 120 \rceil = 7$, since $2^6 = 64 \lt 120 \le 128$.

(c)

Insertion sort's worst case is the reversed list: $1 + 2 + \dots + (N-1) = N(N-1)/2$ comparisons.

Merge sort for $N=4$: two 1+1 merges (1 each), then a 2+2 merge (at most 3), total 5. For $N=5$ it splits 2 | 3. The 2 side is one comparison. The 3 side is 1 | 2: one for the pair, then at most 2 to merge 1 with 2. The final 2+3 merge is at most 4. Total $1 + 1 + 2 + 4 = 8$. No. "Optimal" in this unit means asymptotically optimal: $\Theta(N \lg N)$ in the worst case, matching the $\Omega(N \lg N)$ bound up to a constant factor. The exact minimum number of comparisons for a specific small $N$ is a different, harder question, and merge sort is one comparison off it at $N = 5$.

How to use this: if an MCQ asks for the minimum worst-case comparisons for a given $N$, compute $\lceil \lg N! \rceil$. Don't read it off merge sort.

A5prove

Prove the three results on slides 21–23, then draw the conclusion on slide 24.

  1. $O(\lg N!) \subseteq O(N \lg N)$.
  2. $O(\lg N!) \supseteq O(N \lg N)$.
  3. Hence $O(\lg N!) = O(N \lg N)$ and $\lg N! \in \Omega(N \lg N)$.
  4. State what this implies for comparison-based sorting, and why merge sort and heapsort are therefore $\Theta(N \lg N)$-optimal.

For (b), write $N!$ twice, once forwards and once backwards, and pair up the factors.

(a) Upper bound

Each of the $N$ factors of $N! = 1 \cdot 2 \cdots N$ is at most $N$, so $N! \le N^N$. Since $\lg$ is increasing, $\lg N! \le \lg N^N = N \lg N$. So $\lg N!$ is bounded above by $N \lg N$, and $O(\lg N!) \subseteq O(N \lg N)$.

(b) Lower bound

Pair the factors of $N!$ with those of $N!$ written backwards: $$N!^2 = \prod_{k=1}^{N} k\,(N-k+1).$$ For each $1 \le k \le N$, $k(N-k+1) - N = (k-1)(N-k) \ge 0$, so every pair is at least $N$. This pairing step is the whole proof: each of the $N$ pairs contributes a factor of at least $N$. Hence $N!^2 \ge N^N$. Taking logs, $2\lg N! \ge N \lg N$, so $\lg N! \ge \tfrac12 N \lg N$. That is, $N \lg N$ is bounded above by a constant times $\lg N!$, and $O(N \lg N) \subseteq O(\lg N!)$.

The slides write strict $\gt$. It should be $\ge$: equality holds at $N = 1$ and $N = 2$. The asymptotic conclusion is unaffected.

(c) Equality

The two set inclusions together give $O(\lg N!) = O(N \lg N)$. Part (b) alone says $\lg N! \ge \tfrac12 N\lg N$, which is the definition of $\lg N! \in \Omega(N \lg N)$.

(d) Conclusion

By A4(a), any comparison sort makes at least $\lceil \lg N! \rceil$ comparisons in the worst case, and that is $\Omega(N \lg N)$. Merge sort and heapsort are $O(N \lg N)$ in the worst case. Upper bound equals lower bound, so both are $\Theta(N \lg N)$: no comparison sort can beat them asymptotically.

The moral: the bound is about comparisons. Part C escapes it only by doing something other than comparing.

Optional · Counting Inversions. Given a list of $N$ integers ($1 \le N \le 2 \times 10^5$, values $|x| \le 10^9$), output the number of pairs $i \lt j$ with $x_j \lt x_i$. An $O(N^2)$ double loop will time out.

Input: a line with $N$, then a line of $N$ integers. Output: one integer.

Sample inputSample output
6
6 3 8 2 7 3		8
5
1 2 3 4 5		0
4
4 3 2 1		6
Idea

Slide 12: each time the merge takes from rhs, that element is smaller than everything still waiting in lhs. So add len(lhs) - li to the count at that moment. $O(N \lg N)$.

Solution 
import sys

def sort_count(a):
    if len(a) <= 1:
        return a, 0
    m = len(a) // 2
    l, x = sort_count(a[:m])
    r, y = sort_count(a[m:])
    res, i, j, c = [], 0, 0, x + y
    while i < len(l) and j < len(r):
        if l[i] <= r[j]:
            res.append(l[i]); i += 1
        else:
            res.append(r[j]); j += 1
            c += len(l) - i          # r[j] jumps every remaining l element
    res += l[i:] + r[j:]
    return res, c

data = sys.stdin.read().split()
n = int(data[0])
print(sort_count(list(map(int, data[1:1 + n])))[1])

Part B · Quicksort

6 questions · ~30 min

Lecture 3, slides 3–27. The one idea to hold onto: partition removes every inversion between L and R in one $O(n)$ pass, so the speed depends entirely on where the pivot lands. B2 is the trace the exam will ask for; B5 is the stability counterexample you should be able to produce on demand.

  3. Define an inversion, and count the inversions in [3, 1, 4, 1, 5].
(a)

Optimal: $O(N \lg N)$ time, matching the comparison lower bound.

In-place (CLRS): only a constant number of list elements are ever stored outside the list.

Stable: elements that compare equal keep their original relative order.

(b)

(c)

An inversion is a pair of elements where the earlier one is strictly greater than the later one. In [3, 1, 4, 1, 5]: 3 before the first 1, 3 before the second 1, and 4 before the second 1. That's 3. The two 1s are equal, so they don't form an inversion.

B4prove
  1. Write partition and quicksort cold.
  2. Give the lecture's argument that quicksort is $O(N \lg N)$ in the expected case. State the assumption about inputs and say where it is used.
  3. Explain how to limit the call stack to $O(\lg N)$ even in the worst case.

For (b), call a split "good" if the pivot lands in the middle half. How much does a good split shrink the problem, and how often do you get one?

(a) Pseudocode 
partition(xs, lwr, upr):           # partitions xs[lwr:upr], returns pivot index
    pivot = xs[upr-1]
    mid = lwr
    for i in lwr .. upr-1:
        if xs[i] <= pivot:
            swap xs[mid], xs[i]
            mid += 1
    return mid - 1                  # pivot was the last element swapped down

quicksort_range(xs, lwr, upr):
    if upr - lwr > 1:
        p = partition(xs, lwr, upr)
        quicksort_range(xs, lwr, p)       # L, pivot excluded
        quicksort_range(xs, p+1, upr)     # R, pivot excluded
(b) Expected case

Assumption: every permutation of the input is equally likely. Then the pivot's final position is uniform over the range.

Good split: the pivot lands in the middle half, between positions $n/4$ and $3n/4$, so each side has at most $3n/4$ elements. This is exactly where the uniformity assumption is used: a uniform position lands in the middle half with probability $1/2$.

Depth: along any root-to-leaf path, each good split multiplies the size by at most $3/4$. Starting from $N$, at most $\log_{4/3} N$ good splits reduce it to 1. Half the splits are good in expectation, so the expected depth is at most $2\log_{4/3} N = O(\lg N)$, since all log bases differ by a constant factor.

Work per level: the ranges at one depth are disjoint, so partitioning them costs $O(N)$ in total.

Depth $O(\lg N)$ times $O(N)$ per level gives $O(N \lg N)$ expected.

(c) Stack

Recurse into the smaller side first, then handle the larger side with a loop instead of a second recursive call (tail-call elimination). Each recursive call is on at most half the current range, so the stack depth is at most $\lg N$, even when the splits are terrible.

Common error: claiming the worst case becomes $O(N \lg N)$ this way. It doesn't. Only the space is bounded; the time is still $O(N^2)$.

B5compute

Label equal keys with letters so you can track their order. Run the lecture's quicksort on [2a, 2b, 1], comparing keys only.

  1. Show the list after each swap of each partition, and the final output.
  2. Explain in one sentence what went wrong, using slide 24's description.
(a)

Partition [0,3), pivot 1. At $i=0$ and $i=1$, 2a and 2b are both $\gt 1$, so nothing moves. At $i=2$, 1 $\le$ 1, so swap positions 0 and 2: [1, 2b, 2a]. The pivot index is 0.

Partition [1,3), pivot 2a. At $i=1$, 2b $\le$ 2a, so swap position 1 with itself; mid becomes 2. At $i=2$, 2a $\le$ 2a, so swap position 2 with itself. Nothing changes.

Final: [1, 2b, 2a]. Sorted by key, but 2b now comes before 2a, so the sort is not stable.

(b)

To bring 1 down, partition swapped it with 2a, the first element greater than the pivot, which threw 2a over the equal key 2b in one long-range swap. Later partitions never undo this: equal keys compare $\le$ each other and are never swapped back.

How to use this: three elements is the smallest counterexample to stability. Write this one down as your standard answer.

B6compute

A pivot gives a bad split if its final position falls in the first or last quarter of the list. Model each randomly sampled element's position as independent and uniform. Compute the probability of a bad split when the pivot is:

  1. one random element;
  2. the median of 3 random elements;
  3. the median of 5 random elements, and compare with slide 26.

The median of $k$ (odd) samples is in the first quarter exactly when more than half of the samples are. Count that with the binomial distribution, then double it for the last quarter.

Set-up

Each sample is in the first quarter with probability $1/4$. The median of $k$ samples is in the first quarter iff at least $(k+1)/2$ of them are. By symmetry, the last quarter has the same probability, and the two events are disjoint.

(a) $k = 1$

$2 \times \tfrac14 = \tfrac12$.

(b) $k = 3$

$P(\ge 2 \text{ of } 3) = \binom32 \left(\tfrac14\right)^2 \tfrac34 + \left(\tfrac14\right)^3 = \tfrac{9}{64} + \tfrac{1}{64} = \tfrac{10}{64}$. Doubled: $\tfrac{20}{64} = \tfrac{5}{16} = 0.3125$.

(c) $k = 5$

$P(\ge 3 \text{ of } 5) = \tfrac{10 \cdot 9}{1024} + \tfrac{5 \cdot 3}{1024} + \tfrac{1}{1024} = \tfrac{106}{1024}$. Doubled: $\tfrac{212}{1024} = \tfrac{53}{256} \approx 0.207$.

Erratum, Lecture 3 slide 26. The slide gives the bad-split probability for median-of-5 as $1/32 \approx 0.031$. The binomial calculation gives $53/256 \approx 0.207$, and a 200,000-trial simulation agrees (0.207). The slide's claim that the median of 5 improves the odds is right; the number is about seven times too optimistic.

Checks

The sequence $0.5 \to 0.3125 \to 0.207$ shrinks as $k$ grows, as it should. Simulation gave 0.502, 0.313 and 0.207 ✓.

The same slide also says to "want the pivot as far from the median as possible". That's the adversary's aim when constructing a bad input, not ours.

Sample inputSample output
8
5 5 5 1 9 5 5 2		1 2 5 5 5 5 5 9
6
1 2 3 4 5 6		1 2 3 4 5 6
Idea

A random pivot defeats sorted input (slide 26). A three-way partition into $\lt$, $=$ and $\gt$ the pivot defeats equal keys, since the whole "=" block is finished in one pass (B3(b)). An explicit stack avoids Python's recursion limit.

Solution 
import sys, random

data = sys.stdin.read().split()
n = int(data[0]); a = list(map(int, data[1:1 + n]))
stack = [(0, n)]
while stack:
    lo, hi = stack.pop()
    if hi - lo <= 1:
        continue
    p = a[random.randrange(lo, hi)]
    lt, i, gt = lo, lo, hi           # a[lo:lt] < p, a[lt:i] == p, a[gt:hi] > p
    while i < gt:
        if a[i] < p:
            a[lt], a[i] = a[i], a[lt]; lt += 1; i += 1
        elif a[i] > p:
            gt -= 1; a[gt], a[i] = a[i], a[gt]
        else:
            i += 1
    stack.append((lo, lt)); stack.append((gt, hi))
print(" ".join(map(str, a)))

Tested on both samples and on random inputs against sorted. 200,000 equal values run in well under a second.

C5prove
  1. Write counting_sort(xs, key) cold and state its time and space complexity in terms of $N$ and $k$.
  2. Prove that LSD radix sort is correct. State the invariant and prove it by induction on the number of passes.
  3. Is radix sort stable? Is it in-place?

Invariant: after $p$ passes, the list is sorted by its last $p$ digits. In the inductive step, split into the cases "digit $p$ differs" and "digit $p$ is equal".

(a) Pseudocode 
counting_sort(xs, key):
    k = max(key(x) for x in xs) + 1
    counts = [0] * k
    for x in xs: counts[key(x)] += 1          # how many per block
    for j in 1 .. k-1: counts[j] += counts[j-1]   # upper bound of each block
    result = [None] * len(xs)
    for x in reversed(xs):                    # reversed: keeps it stable
        counts[key(x)] -= 1
        result[counts[key(x)]] = x
    return result

Time $O(N + k)$: two passes over the input and one over the counts. Extra space $O(N + k)$ for result and counts, so it is not in-place.

Common error: calling it $O(N)$ without conditions. It is $O(N)$ only when $k = O(N)$; sorting 10 values up to $10^9$ costs $10^9$.

(b) Correctness

Invariant $I(p)$: after $p$ passes, the list is sorted by the number formed from each element's last $p$ digits.

Base: $I(0)$ holds trivially, since every element has the same empty suffix.

Step: assume $I(p)$, and run pass $p+1$, which sorts on digit $p$ (counting from 0 at the right). Take any two elements $a$ and $b$ whose last $p+1$ digits satisfy $a \lt b$.

Case 1: digit $p$ of $a$ is less than digit $p$ of $b$. The pass sorts by that digit, so $a$ is placed before $b$.

Case 2: their digit $p$ is equal. Then $a \lt b$ must be decided by the lower $p$ digits, so by $I(p)$, $a$ was before $b$ going into the pass. This step is exactly where stability of the inner sort is used: a stable sort keeps equal keys in their incoming order, so $a$ stays before $b$.

Either way $a$ ends up before $b$, so $I(p+1)$ holds. After $d$ passes, $I(d)$ says the list is sorted by every digit. ∎

Without stability, Case 2 fails, which is exactly what C3(c) shows.

(c)

Radix sort is stable, because each pass is stable: equal elements tie on every digit and are never reordered. It is in-place only if the inner sort is, and counting sort is not (slide 16).

(a)

The $i$th order statistic of $n$ elements is the $i$th smallest. The selection problem: given a set $A$ and $i \in [1, n]$, find the $x \in A$ that is greater than exactly $i - 1$ other elements of $A$.

The lower median is the $\lfloor (n+1)/2 \rfloor$th and the upper median the $\lceil (n+1)/2 \rceil$th.

(c)

Build a heap in $O(n)$, then pop $i$ times at $O(\lg n)$ each: $O(n + i \lg n)$. That's $O(n \lg n)$ in the worst case.

For $i$ past halfway, flip the comparison and pop $n - i + 1$ elements instead. This saves at most a factor of 2.

(d)

Introselect runs quickselect, but falls back to heapselect if the recursion gets deeper than $O(\lg n)$ (typically $2\log_2 n$). It is in-place, has quickselect's expected behaviour, and guarantees $O(n \lg n)$ in the worst case. That is still not $O(n)$, which is why median of medians exists.

D4prove
  1. Explain why the median of medians is greater than about $3n/10$ elements, and less than about $3n/10$.
  2. Write the recurrence, and prove by induction that $T(n) \le 10cn$.
  3. Show what goes wrong with groups of 3.
  4. If median of medians is worst-case $O(n)$, why does the lecture say random pivots are usually faster?

For (c), redo the counting with 3 instead of 5, then add up the two fractions in the recurrence. Compare the sum with 1.

(a)

There are $n/5$ groups, so $|A'| = n/5$. The median $m$ of $A'$ is greater than half of them, about $n/10$ group medians. Each of those medians is greater than 2 more elements of its own group, so each accounts for 3 elements of $A$ that are below $m$. That gives at least $3 \cdot n/10 = 3n/10$ elements below $m$, and the same argument with "less than" gives $3n/10$ above.

So the recursion goes into at most $n - 3n/10 = 7n/10$ elements.

(b) Recurrence and induction

Finding the group medians and partitioning cost $cn$. Finding the median of the $n/5$ medians is a recursive call, and the recursion into one side is another: $$T(n) \le cn + T\!\left(\tfrac{n}{5}\right) + T\!\left(\tfrac{7n}{10}\right).$$

Claim: $T(n) \le 10cn$. By strong induction on $n$: for small $n$ (the base case, $n \le 5$, solved directly) it holds with $c$ chosen large enough. For the step, assume the claim for every size below $n$. Both $n/5$ and $7n/10$ are smaller than $n$, so $$T(n) \le cn + 10c\tfrac{n}{5} + 10c\tfrac{7n}{10} = cn + 2cn + 7cn = 10cn.$$ This step is exactly where $\tfrac15 + \tfrac{7}{10} = \tfrac{9}{10} \lt 1$ is used: the two subproblems together are a constant fraction smaller than $n$, so the work shrinks geometrically. Hence $T(n) \in O(n)$. ∎

(c) Groups of 3

Each group median is greater than 1 other element, and $m$ beats about $n/6$ of the $n/3$ medians. That's only $2 \cdot n/6 = n/3$ elements guaranteed below $m$, so the recursion may go into $2n/3$: $$T(n) \le cn + T\!\left(\tfrac n3\right) + T\!\left(\tfrac{2n}{3}\right), \qquad \tfrac13 + \tfrac23 = 1.$$ The subproblems no longer shrink in total; every level still costs $cn$. With $O(\lg n)$ levels, that's $O(n \lg n)$. Five is the smallest group size that gets the fractions to add up to less than 1.

(d)

The constant is large: up to $10c$, plus a second recursion at every step. A random pivot (or the median of a few random samples) gets $O(n)$ expected with a much smaller constant, and its worst case is astronomically unlikely. Use median of medians only when you need the guarantee.

(a) Definitions

Inversion: a pair with the earlier element strictly greater than the later one. Stable: equal elements keep their original relative order. In-place (CLRS): only $O(1)$ list elements are ever held outside the list. Strong key: $x \lt y \Rightarrow \text{key}(x) \lt \text{key}(y)$. Weak key: $x \lt y \Rightarrow \text{key}(x) \le \text{key}(y)$. $i$th order statistic: the $i$th smallest element. Selection: given $A$ and $i \in [1, n]$, find the $x \in A$ greater than exactly $i - 1$ others.

(b) Lower bound

Any comparison sort makes at least $\lceil \lg N! \rceil$ comparisons in the worst case, since its decision tree has $\ge N!$ leaves and a tree of height $h$ has $\le 2^h$ leaves. The two inequalities: $N! \le N^N$, and $N!^2 \ge N^N$ because $k(N-k+1) \ge N$. Together they give $\tfrac12 N \lg N \le \lg N! \le N \lg N$.
