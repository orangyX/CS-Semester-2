A1recall

Read the spec against the source's own definitions and its point of comparison.

  1. Define a spanning tree and a minimum spanning tree.
  2. State Kruskal's rule in one sentence: what does the algorithm do, start to finish?
  3. Prim's (slide 3) also builds an MST greedily, one edge at a time. In one sentence, what's the structural difference between what the two algorithms are greedily choosing from at each step?
  4. Sample 3 has 3 vertices and needs exactly 2 edges, whichever spanning tree you pick. Why does every spanning tree on $n$ vertices have exactly $n-1$ edges, regardless of which one it is?
(a) Definitions

A spanning tree of $G=(V,E)$ is a subgraph $T=(V,E')$ that is itself a tree (connected, acyclic) and contains every vertex of $G$. A minimum spanning tree is a spanning tree whose total edge weight is as small as possible.

(b) The rule

Start with every vertex in its own single-vertex tree; consider every edge once, in increasing order of weight; add an edge whenever its two endpoints currently sit in different trees; stop once one tree remains.

(c) What each algorithm chooses from

Prim's grows one tree and, at each step, chooses among only the edges with exactly one endpoint already in that tree — a frontier that changes shape every step. Kruskal's never tracks a frontier at all: it looks at every edge in the whole graph, sorted once up front, and decides validity only at the moment each edge is considered, against whichever trees happen to exist at that point.

(d) Why $n-1$, always

By induction on $n$. A single vertex ($n=1$) is a tree with $0=n-1$ edges. Given a tree on $n-1$ vertices with $n-2$ edges, attaching one new vertex to it requires exactly one new edge to keep the result connected — and adding exactly one edge to a tree, to a genuinely new vertex, cannot create a cycle. This is where "tree" doing double duty as both "connected" and "acyclic" is used: a spanning tree with more than $n-1$ edges would have to contain a cycle (too many edges to stay acyclic on $n$ vertices), and one with fewer couldn't reach every vertex. Exactly $n-1$ is the only count that can do both.

Implementation 
class DisjointSets:
    def __init__(self, n):
        self.parent = [i for i in range(n)]
        self.rank = [0 for _ in range(n)]

    def find(self, i):
        root = i
        while self.parent[root] != root:
            root = self.parent[root]
        curr = i
        while self.parent[curr] != curr:
            nxt = self.parent[curr]
            self.parent[curr] = root
            curr = nxt
        return root

    def union(self, i, j):
        i, j = self.find(i), self.find(j)
        if i == j:
            return
        if self.rank[i] < self.rank[j]:
            i, j = j, i
        self.parent[j] = i
        self.rank[i] = max(self.rank[i], self.rank[j] + 1)


def mst_weight(n, edges):
    sets = DisjointSets(n)
    total = 0
    for u, v, w in sorted(edges, key=lambda e: e[2]):
        if sets.find(u) != sets.find(v):
            total += w
            sets.union(u, v)
    return total

if __name__ == "__main__":
    n, m = map(int, input().split())
    edges = [tuple(map(int, input().split())) for _ in range(m)]
    print(mst_weight(n, edges))

A4prove

Cost A3's implementation.

  1. Sorting $m$ edges costs $O(m\log m)$. Using the plain (not amortised) worst-case bound for disjoint-set operations that C4 proves — $O(\log n)$ per find or union, for $n$ vertices — give the cost of the main loop.
  2. Combine the two to state the overall complexity, and simplify it: for a connected graph, explain why $\log m$ and $\log n$ are the same order, so the two terms collapse into one.
  3. Contrast with the naive array-based version from slide 6, costed on slide 7 as $O(n^2 + m\log m)$. For a sparse graph ($m$ close to $n$) versus a dense one ($m$ close to $n^2$), which term dominates the naive version in each case?

For part (b): a connected graph has $n-1\le m\le \binom{n}{2}$. Take logs of both bounds and see what that forces about how $\log m$ relates to $\log n$.

(a) The main loop

The loop does 2 finds per edge (to check) and up to 1 union (if added): $O(m)$ disjoint-set operations, each $O(\log n)$ worst case, giving $O(m\log n)$ for the loop.

(b) Collapsing the two terms

For a connected graph, $n-1\le m\le\binom{n}{2}=O(n^2)$. Taking logs: $\log(n-1) \le \log m \le O(\log n)$ (since $\log(n^2)=2\log n$). So $\log m$ and $\log n$ are both $\Theta(\log n)$ — the same order — meaning $O(m\log m)+O(m\log n)=O(m\log m)$. The overall cost is $O(m\log m)$, exactly the figure slide 23 states.

(c) Sparse versus dense, for the naive version

Sparse ($m\approx n$): $n^2$ dominates $m\log m\approx n\log n$ — the naive version's array-scan is the bottleneck, exactly the case the lecture motivates disjoint sets with. Dense ($m\approx n^2$): $m\log m \approx n^2\log n$ now dominates $n^2$ — sorting becomes the bottleneck instead, and the naive version's $O(n^2)$ union cost stops being the limiting factor.

Why this matters: the disjoint-set upgrade is most valuable exactly where graphs actually tend to be — sparse. On a dense graph the two versions are asymptotically much closer, since sorting dominates either way.

B1compute

Trace why the data structure needs the shape it has, using the source's own progression (slides 6, 10–11).

  1. In the naive tree[] array (slide 6), which of find/union is expensive, and why?
  2. The first fix (slide 11) is to store a parent pointer instead of a leader directly. Which operation becomes expensive instead, and why does the trade happen at all?
  3. With only that fix — parent pointers, no union-by-height, no compression — show that a bad sequence of unions can still make a single find cost $\Theta(n)$.
(a) The array version

find is a single array lookup, $O(1)$. union has to overwrite the leader for every element currently in one of the two sets — an $O(n)$ scan over the whole array, since nothing records which elements belong to which set except by scanning to find them.

(b) The trade

Pointing each element at its parent instead of its leader makes union $O(1)$ — attach one root under the other, nothing else moves. The cost shifts to find, which must now walk from an element up through however many parent links separate it from its root — $O(\text{height of its tree})$, $O(n)$ in the worst case. Nothing was solved for free: the $O(n)$ cost that used to sit in union just relocated to find.

(c) A concrete $\Theta(n)$ chain

Call union(1,0), then union(2,1), then union(3,2), …, up to union(n-1,n-2), with union always attaching the second argument's root under the first's. Each call attaches the entire tree built so far underneath a single fresh element, extending the chain by exactly one link every time: $0\to1\to2\to\cdots\to(n-1)$. find(0) now walks all $n-1$ links to the root — verified directly: for $n=6$ this sequence produces the parent array $[1,2,3,4,5,5]$, and find(0) takes exactly 5 steps.

Why this matters: this exact failure mode is what union-by-height (slide 13) is built to rule out — B4 and C4 pick this back up.

Cost B2's implementation, contrasting the two bounds the lecture actually gives.

  1. C4 proves a tree built under union-by-rank has height $O(\log n)$. State what this gives as the worst-case cost of a single find or union, and hence of $q$ operations total.
  2. Slide 22 states a better bound for the combination of path compression and union by rank — $O(q\,\alpha(n))$ for $q$ operations — but says the proof is "too complicated to present." (a) The provable bound

Height $O(\log n)$ means a single find (and hence union, which calls two finds) costs $O(\log n)$ in the worst case. $q$ operations therefore cost $O(q\log n)$ overall — already a world away from B1(c)'s $\Theta(n)$ single-find disaster.

(b) What "amortised" claims that worst-case-per-op doesn't

A worst-case-per-operation bound says every single operation costs at most that much. An amortised bound says something weaker but still useful: averaged over the whole sequence of $q$ operations, the cost per operation is at most $\alpha(n)$ — some individual finds can still cost more than that (an expensive find right after a long chain of unions is exactly when path compression has the most to flatten), but the sheet's own bound already builds in why: an expensive find can only happen after enough unions to build a tall path, and it pays for its own expense by flattening that path for everyone after it.

C1prove

Prove the cut property: for any partition of the vertices into nonempty $S$ and $V\setminus S$, if $e$ is a minimum-weight edge with exactly one endpoint in $S$, then some MST contains $e$.

Take any MST $T$ that doesn't already contain $e$. Adding $e$ to $T$ creates exactly one cycle — think about how many times that cycle can cross the cut $(S, V\setminus S)$, and what that forces about the cycle's other edges.

Set-up

Let $T$ be any MST. If $e\in T$, done. Otherwise, $T+e$ contains exactly one cycle $C$ (a spanning tree plus one extra edge always creates exactly one cycle, through that edge).

Finding a partner edge

$C$ is a cycle, so it must return to whichever side of the cut it started on — it crosses $(S,V\setminus S)$ an even number of times. $e$ itself is one crossing, so $C$ contains at least one other edge $f\ne e$ that also crosses the cut.

The swap

Since $e$ is a minimum-weight edge crossing this cut, and $f$ also crosses it: $w(e)\le w(f)$. Form $T' = T - f + e$. Removing $f$ breaks cycle $C$ back into a tree shape; since both $e$ and $f$ cross the same cut, $e$ reconnects exactly the two pieces $f$'s removal separated — $T'$ is a valid spanning tree.

Conclusion

$\text{weight}(T') = \text{weight}(T) - w(f) + w(e) \le \text{weight}(T)$. But $T$ was already optimal, so nothing can cost less: $\text{weight}(T')\ge\text{weight}(T)$ too. Hence $\text{weight}(T')=\text{weight}(T)$ — $T'$ is also an MST, and it contains $e$. $\blacksquare$

C2prove

Show that every edge Kruskal's selects satisfies C1's hypothesis — and that this is enough to conclude Kruskal's produces an MST, not just that each individual edge is somewhere safe.

Kruskal's edge is minimum over its own cut

Say Kruskal's selects $\{u,v\}$, with $U$ = $u$'s current tree. Take any edge $\{x,y\}$ crossing $(U,V\setminus U)$, i.e. $x\in U, y\notin U$. Suppose for contradiction $w(x,y) \lt w(u,v)$ — then Kruskal's processes $\{x,y\}$ strictly earlier (sorted order). At that earlier moment, either $x,y$ were already in the same tree, or they weren't:

  • If they weren't, $\{x,y\}$ connects two different trees and has already been reached in the sort order, so Kruskal's adds it — merging $x$ and $y$ into the same tree from then on.
  • If they already were in the same tree, $y$ was already merged with $x$ before this point.

Either way, $y$ ends up in $x$'s tree — and since $x\in U$, that means $y\in U$. This contradicts $y\notin U$. So no edge crossing $(U,V\setminus U)$ is lighter than $\{u,v\}$: it is a minimum-weight edge across this cut, exactly C1's hypothesis.

Why one-safe-edge-at-a-time is enough

Induct on the number of edges added. Claim: after Kruskal's has added $e_1,\ldots,e_k$, there is an MST $T_k$ containing all of them. Base case $k=0$: any MST works. For the step, apply C1's own proof — not just its conclusion — to $T_k$ and the cut $(U,V\setminus U)$ that makes $e_{k+1}$ safe: if $e_{k+1}\notin T_k$, swap it in for some other cut-crossing edge $f$ in the resulting cycle, giving $T_{k+1}$.

The one thing that needs checking: $f$ can never be one of $e_1,\ldots,e_k$. Every edge Kruskal's has already added is now internal to some tree in Kruskal's forest — both its endpoints share a tree — so it cannot cross the cut $(U, V\setminus U)$ between two currently-different trees. $f$ crosses that cut by construction, so $f\ne e_i$ for every $i\le k$. $T_{k+1}$ therefore contains $e_1,\ldots,e_k,e_{k+1}$, all at once.

At the end, $n-1$ edges have been added and there is an MST containing all of them — a set of $n-1$ edges that forms a spanning tree and sits inside an MST of the same size must simply be that MST. $\blacksquare$

C3prove

A5 showed the 4-cycle graph gives total $3$ either way, but excludes a different edge depending on processing order. Use C1's own proof to show exactly why this had to be possible.

Re-examine the one inequality C1 actually needs: $w(e)\le w(f)$, used to conclude $\text{weight}(T')\le\text{weight}(T)$. Nothing in the proof requires this to be a strict inequality — $\le$ is exactly what's stated and exactly what's used.

On the 4-cycle, every edge has weight $1$. Whichever edge plays the role of $e$ (the one being swapped in) and whichever plays $f$ (the one being swapped out), $w(e)=w(f)=1$: the inequality is always an equality. C1's proof concludes $T'$ is also an MST whenever this holds — it never claims $T$ was wrong to use $f$ instead of $e$. Since every pair of edges on this cycle ties, the proof is silent on which one "should" be excluded — it only guarantees that whichever choice gets made, the total is preserved.

Why this matters: this is the graph analogue of the Huffman sheet's C6 — re-examining an exchange argument's own inequality to see exactly where it stops distinguishing between tied alternatives. The mechanism is identical; only the objects being exchanged (edges vs. codeword positions) differ.

C4prove

Prove slide 15's claim: under union by height, a tree of height $h$ contains at least $2^h$ elements. Conclude that a tree built from $n$ elements has height at most $\log_2 n$.

First pin down exactly when a merge can increase height at all, using the rank-update rule $\text{new\_height} = \max(\text{taller's height}, \text{shorter's height}+1)$ — then induct on $h$.

When height actually increases

Merging a tree of height $h_i$ (becoming the new root) with one of height $h_j\le h_i$ gives new height $\max(h_i, h_j+1)$. If $h_i \gt h_j$, then $h_i\ge h_j+1$, so the max is just $h_i$ — height only changes when $h_i=h_j$ exactly, in which case it becomes $h_i+1$. A tree reaches height $h\ge1$ only by merging two trees that were both already at height $h-1$.

Induction

Let $n(h)$ be the minimum possible size of a height-$h$ tree. Base case $h=0$: a single node, $n(0)=1=2^0$. Step: a height-$h$ tree ($h\ge1$) is the union of two height-$(h-1)$ trees, each with at least $n(h-1)$ elements by the inductive hypothesis, so $n(h)\ge 2\,n(h-1) \ge 2\cdot 2^{h-1} = 2^h$. $\blacksquare$

The height bound

If a tree built from $n$ elements had height $h$, it would need at least $2^h$ elements — so $2^h\le n$, giving $h\le\log_2 n$.

Independent check: the bound is tight, not just an upper estimate — repeatedly pairing equal-sized groups (1,1 $\to$ 2; 2,2 $\to$ 4; 4,4 $\to$ 8; …) was simulated directly for $h=0$ through $5$ and produced a tree of exactly height $h$ from exactly $2^h$ elements every time. ✓

In the same terms the Huffman sheet's C5 uses: what does C1 establish (the greedy-choice property for this problem), what does C2 add on top of it, and why doesn't "this one edge is safe" by itself already prove Kruskal's produces an MST?

Greedy-choice property (C1): for any cut, a minimum-weight edge crossing it is always safe to add — some MST contains it. C2 shows two things: first, that every edge Kruskal's actually selects satisfies exactly this hypothesis at the moment it's selected; second — the part that closes the real gap — that repeating this doesn't just land in some MST at each step, it lands in an MST containing every edge already added, because none of those earlier edges can ever be the one swapped out.

Why "one edge is safe" isn't automatically enough: being told each individual choice doesn't hurt says nothing about whether the choices stay compatible with each other over time — a sequence of moves that are each locally fine could still, in principle, contradict each other collectively. What actually licenses Kruskal's is the inductive invariant C2 proves: the growing edge set is, at every single step, a subset of one common MST — so by the last step, when it's a full spanning tree in its own right, it doesn't just resemble an MST, it is the one it's been a subset of all along.

C6recall

Slide 22 states, without proof, that path compression plus union by rank gives $O(m\,\alpha(n))$ for $m$ operations on $n$ elements.

  1. State what $\alpha(n)$ is, and explain — without proving the complexity result itself — why the Ackermann function's explosive growth forces $\alpha(n)$ to grow correspondingly slowly.
  2. C4 already proves a worst-case bound of $O(\log n)$ per operation. What does slide 22's result improve, precisely, and what does $\alpha(n)\le 4$ "for all practical purposes" actually buy over $m$ operations each costing $O(\log n)$?
(a) What $\alpha(n)$ is, and why it's slow

$\alpha(n)$ is defined as the smallest $k$ such that $A_k(k)\ge n$, where $A_k$ is the Ackermann function. Because $A_k(k)$ grows so fast that it passes any fixed, fathomable number almost as soon as $k$ ticks up by one — the source's own example is $A_4(4)$ already exceeding the number of atoms in the observable universe — $\alpha$, which asks "how large does $k$ need to be before $A_k(k)$ catches up to $n$," barely has to move at all even for enormous $n$. An inverse of an extremely fast-growing function is, definitionally, an extremely slow-growing one.

(b) What actually improves

C4's bound is worst-case per operation: every single find or union costs at most $O(\log n)$, full stop. Slide 22's bound is amortised over the whole sequence: $m$ operations cost $O(m\,\alpha(n))$ total, not $O(m\log n)$. Since $\alpha(n)\le4$ for any $n$ you could actually construct, this means $m$ operations cost, in total, barely more than $O(m)$ — the per-operation cost effectively becomes a small constant once amortised, rather than growing (even slowly, as $\log n$) with the size of the structure.

C7prove

Problem A's spec guarantees a connected graph. Neither the naive (slide 6) nor the efficient (slide 23) implementation actually checks this.

  1. Trace mst_weight on $n{=}3$ with a single edge $\{0,1{:}5\}$ — vertex $2$ has no edges at all. What does the function return?
  2. Is the number it returns the weight of a spanning tree? Prove your answer using A1(d)'s own fact about spanning trees.
  3. Propose one small change to the implementation that would let it detect this situation instead of silently returning a number.
(a) What it returns

The single edge $\{0,1\}$ connects two different trees, so it's added; total returned: $5$. No exception, no warning — the function returns a plain, unremarkable-looking integer.

(b) Not a spanning tree

No. By A1(d), any spanning tree on $n=3$ vertices needs exactly $n-1=2$ edges. Only $1$ edge was added here. The "$5$" is the weight of a spanning tree of the subgraph on $\{0,1\}$ — a spanning forest of the whole graph, covering 2 of 3 vertices, not a spanning tree of it. The function's return type promises a single number either way, so there is nothing in the output itself that distinguishes "the MST weight" from "the weight of whatever forest happened to result."

(c) A fix

Count the number of edges actually added (equivalently, the number of successful, non-"already" unions). If that count is ever less than $n-1$ once every edge has been considered, the graph was disconnected — raise an error, or return the forest's weight paired with how many components remain, rather than a bare integer that looks identical to a genuine MST weight either way.

Why this matters: this is the same shape of gap as the Huffman sheet's C7 — the algorithm's stated correctness proof (C1–C2 here) implicitly assumes the setting its hypotheses actually hold in, and the code doesn't verify that assumption before running.

D2prove

Slide 23's $O(E\lg E)$ is dominated entirely by the sort.

  1. If the edges arrive already sorted by weight — no sort needed — what does the overall complexity become?
  2. Even for unsorted input, is a comparison-based sort the only option? Name one situation where a non-comparison sort could still get the whole algorithm down to that same complexity.
(a) Skipping the sort

What's left is just the disjoint-set operations: $O(E\,\alpha(V))$ by slide 22's amortised bound, which — since $\alpha(V)\le4$ for any $V$ you could construct — is $O(E)$ in every practical sense. Removing the sort doesn't shave a log factor off; it removes the only super-linear term in the whole algorithm.

(b) A non-comparison route

If edge weights are small integers within a known bounded range (say $0$ to $W$), counting sort or radix sort can sort the $E$ edges in $O(E+W)$ time rather than $O(E\log E)$ — sidestepping the $\Omega(E\log E)$ lower bound that applies only to comparison-based sorting. Whenever that assumption holds, the whole algorithm drops to $O(E)$ even from a cold, unsorted start.

D3compute

Each of these is a final (parent, rank) state. Which could actually result from the lecture's DisjointSets class, and which couldn't?

  1. $n{=}4$: parent $=[0,0,0,0]$, rank $=[2,0,0,0]$
  2. $n{=}3$: parent $=[1,0,2]$
  3. $n{=}4$: parent $=[0,0,0,0]$, rank $=[3,0,0,0]$
  4. $n{=}3$: parent $=[1,1,1]$, rank $=[0,1,0]$
  5. $n{=}8$: parent $=[3,3,3,3,3,3,3,3]$, rank $=[0,0,0,3,0,0,0,0]$
1 — valid

Root $0$ has rank $2$ and its set has all $4$ elements. C4 requires size $\ge 2^{\text{rank}}=4$: exactly met. Achievable by, e.g., merging $\{0,1\}$ and $\{2,3\}$ (each rank $1$) together.

2 — invalid: not a valid forest at all

parent$[0]{=}1$ and parent$[1]{=}0$ is a 2-cycle. Neither $0$ nor $1$ is ever recognised as a root, and find would loop forever rather than terminate. This can't arise from any sequence of correct union calls, which only ever attach a root under another root — never create a cycle.

3 — invalid: rank exceeds what the set size supports

Root $0$ claims rank $3$, which by C4 needs a set of at least $2^3=8$ elements — but only $4$ elements exist in total. This directly contradicts C4: no sequence of union-by-rank merges on $4$ elements can ever produce a rank higher than $2$.

4 — valid

Root $1$, rank $1$, set size $3\ge2^1=2$. Achievable: union(0,1) (tied ranks $0,0$, giving root $1$ if $1$ is passed first — the lecture's code doesn't swap on a tie — rank becomes $1$), then union(1,2) attaches $2$ under the now rank-$1$ root.

5 — valid

Root $3$, rank $3$, set size $8=2^3$: the tight case from C4, achievable by pairing up all $8$ elements two at a time, then pairing the resulting pairs, then pairing those.

Two different flaws, both real: (2) isn't even a valid forest — a structural impossibility with no reference to rank at all; (3) is a perfectly well-formed forest whose rank simply lies about how it could have been built. "Well-formed" and "reachable by this algorithm" are different bars, exactly as B3 found for a single operation and A5/C3 found for edge selection.

D4recall

The lecture builds disjoint sets specifically to serve Kruskal's.

  1. Name one other task — unrelated to spanning trees — that "are these two things already connected, and can I merge them" naturally fits.
  2. Kruskal's and Prim's as presented both assume an undirected graph. What about the cut-property proof (C1) specifically breaks if edges only go one way?
(a) Another natural fit

Finding connected components in an image (grouping adjacent same-coloured pixels into regions) or detecting a cycle while building a graph edge by edge — both are exactly "are these two elements already in the same group, and if not, merge them," with no reference to trees or edge weights at all.

(b) What breaks in a directed setting

C1's proof leans on a cycle crossing the cut "an even number of times" purely because it has to return to where it started — a statement about the cycle's vertex sequence, which holds regardless of edge direction. What actually breaks is earlier: a cut $(S,V\setminus S)$ in a directed graph has edges crossing both ways (some $S\to (V\setminus S)$, some the reverse), and "connects the two sides" no longer means the same thing for both directions — reconnecting a piece severed by removing $f$ isn't guaranteed by adding an edge $e$ that only permits travel in one specific direction. The proof's swap step assumes any cut-crossing edge can serve as a two-way bridge, which is exactly what a directed edge can't do.

1

A spanning tree of $G=(V,E)$ is a subgraph $T=(V,E')$ that is a tree and contains every vertex. A minimum spanning tree is a spanning tree of minimum total edge weight.

2

Sort all edges by weight; process them in increasing order, adding any edge whose endpoints are currently in different trees; stop once one tree remains.

3

For any partition of the vertices into nonempty $S$ and $V\setminus S$, a minimum-weight edge with exactly one endpoint in $S$ is contained in some MST (C1).

4

A tree of height $h$ built under union-by-height has at least $2^h$ elements (C4); equivalently, a tree of $n$ elements has height at most $\log_2 n$, so find and union cost $O(\log n)$ in the worst case.

5

Only how quickly — path compression repoints pointers to the already-determined root; it cannot change which root an element's set has, only how many hops it takes to discover it (C5, C6).

6

$O(E\log E)$; sorting the edges dominates, with the disjoint-set operations contributing only $O(E\,\alpha(V))$ (D2).

7

False. A5 and C3 exhibit two correct runs on the same tied-weight graph that exclude different edges while agreeing on total weight — ties fix the cost, not the specific tree.
