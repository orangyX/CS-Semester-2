Problem A · Encode

Input. One line of text, using at least two distinct characters. Letters, spaces and punctuation all count as characters.

Output. A single integer: the number of bits in an optimal encoding of the input under a binary Huffman code.

A1recall

Read the spec against the source's own fixed-length baseline.

  1. Define a prefix-free code.
  2. Sample 1's alphabet has 9 distinct characters. What would a fixed-length code cost per character, and for the whole 31-character line?
  3. State Huffman's construction rule in one sentence: what does each step of the algorithm actually do?
  4. Sample 3, bbbba, gives an output of 5 — for 5 characters, that's 1 bit each. Explain why a 2-symbol alphabet can never do better than 1 bit per character, under any prefix-free code, Huffman or otherwise.
(a) Prefix-free

A code is prefix-free if no codeword is a prefix of another codeword. That single property is what makes concatenated codewords splittable left to right with no lookahead: the first codeword you can match against the front of the remaining bits is the only one there is, because nothing shorter and nothing longer that started the same way is also in the code.

(b) Fixed-length baseline

$\lceil \lg 9 \rceil = 4$ bits per character. For the 31-character line: $31 \times 4 = 124$ bits — exactly the figure the source computes on slide 4.

(c) The rule

Start with one leaf per symbol, weighted by its frequency; repeatedly take the two lowest-weight nodes currently on the table — leaves or already-merged subtrees, it makes no difference which — and join them under a new parent whose weight is their sum; stop when one tree remains. Each symbol's codeword is then the sequence of left/right choices from the root down to its leaf.

(d) The 2-symbol floor

With exactly two codewords needed and the code required to be prefix-free, neither can be a prefix of the other. A 0-bit codeword is a prefix of every other string, so it is ruled out immediately — both codewords need length $\ge 1$. One bit is already enough to distinguish two things, so length exactly $1$ for both is achievable and therefore optimal: $\lceil \lg 2\rceil = 1$ too, so fixed-length ties Huffman here rather than losing to it.

Why this matters: every "no saving" case on this sheet — sample 3 here, and the balanced cases in D3 — traces back to this one fact. Prefix-freeness has a hard floor, and Huffman can only ever reach that floor, never beat it.

(a)+(b) Implementation 
import heapq
from collections import Counter

def total_bits(text):
    freq = Counter(text)
    if len(freq) == 1:
        return sum(freq.values())          # 1 bit/occurrence by convention -- see (c)

    heap = [[w, i, ch, None, None] for i, (ch, w) in enumerate(freq.items())]
    heapq.heapify(heap)
    node_id = len(heap)
    while len(heap) > 1:
        left  = heapq.heappop(heap)
        right = heapq.heappop(heap)
        merged = [left[0] + right[0], node_id, None, left, right]
        node_id += 1
        heapq.heappush(heap, merged)

    root = heap[0]
    total = 0
    def walk(node, depth):
        nonlocal total
        w, _, ch, left, right = node
        if ch is not None:                 # leaf
            total += w * max(depth, 1)
            return
        walk(left, depth + 1)
        walk(right, depth + 1)
    walk(root, 0)
    return total

if __name__ == "__main__":
    print(total_bits(input()))

Independent check: all three samples (94, 23, 5) and both extra tests (32, 21) reproduce the figures already given. ✓

(c) The single-symbol edge case

$\lg 1 = 0$ is correct as an information-theoretic statement: once you already know every character is a, a stream of as carries no new information, so it costs nothing to describe in the limit. But a 0-bit codeword is unusable in practice — a decoder has to tell "4 repetitions" from "0 repetitions" by reading the bitstream, and an empty codeword produces the empty bitstring either way, so the two cases become indistinguishable.

The fix used above is the one every real implementation uses: fall back to a 1-bit codeword when the alphabet has exactly one symbol, and rely on the character count — which every real format transmits somewhere — to know when to stop. For aaaa that gives $4\times1=4$.

Why this matters: this is the gap between the theoretical entropy bound and what any concrete, decodable code can actually achieve. Huffman gets arbitrarily close to entropy, but staying decodable is what rules out 0 bits here. C7 revisits this same edge case from the algorithm's-correctness side, not the implementation side.

A4prove

Cost the construction itself, not the encoding it produces.

  1. With $n$ distinct symbols in the input — not the input's length — how many merge steps does the algorithm perform, and how many heap push/pop operations does that come to in total, initial pushes included?
  2. Each operation on a heap of size $O(n)$ costs $O(\log n)$. Give the total time to build the tree, and separately the time to compute the initial frequency table from an input of length $N$.
  3. Combine these: what is the overall time complexity of Problem A's solution, in terms of both $N$ and $n$? Under what condition does the $n\log n$ term stop mattering next to the $N$ term?

Count pushes and pops separately before you combine them — don't reason about "the heap's size" directly, reason about how many times something goes in or comes out.

(a) Operation count

$n$ symbols need exactly $n-1$ merges to reach a single tree — each merge reduces the node count by one, from $n$ down to $1$. That's $n$ initial pushes, plus $n-1$ more pushes (one per merge) and $2(n-1)$ pops (two per merge): $2n-1$ pushes and $2n-2$ pops, so $\Theta(n)$ heap operations in total.

(b) Costing it

The heap never holds more than $O(n)$ items, so every operation costs $O(\log n)$: the whole build is $\Theta(n)\times O(\log n) = O(n\log n)$. Computing the frequency table is one linear pass over the input incrementing a hash map — $O(N)$, no comparisons involved.

(c) Overall

$$O(N + n\log n).$$

The $n\log n$ term is dominated by $N$ whenever $n = O(N/\log N)$ — true of nearly every real input, since alphabet size is bounded (256 for raw bytes, far smaller for natural-language text) while $N$ grows without bound. The two terms are only comparable when the input is itself close to the size of its own alphabet: a handful of characters, not the regime this problem is built for.

Independent check: sample 1 has $n=9,\ N=31$, giving $n\log_2 n \approx 28.5$ against $N=31$ — genuinely comparable at this toy size, which is exactly why the dominance claim above is stated as asymptotic, not as something true of sample 1 itself. ✓

B1compute

Before implementing anything, trace what the lecture's own example (slide 5) actually breaks.

  1. The lecture gives $A{=}01,\ B{=}0101$ and says $010101$ could be read as "AB", "BA", or "AAA". Write out all three parses explicitly — which bits belong to which codeword, for each reading.
  2. Which direction of the prefix-free property does this code violate: is $01$ a prefix of $0101$, the reverse, or both?
  3. State precisely what has to be true of a message's first codeword boundary for greedy left-to-right matching — accumulate bits, stop at the first exact table match — to find it correctly every time.
(a) The three parses

"AB": $\underbrace{01}_{A}\,\underbrace{0101}_{B}$. "BA": $\underbrace{0101}_{B}\,\underbrace{01}_{A}$. "AAA": $\underbrace{01}_{A}\,\underbrace{01}_{A}\,\underbrace{01}_{A}$. All three consume exactly the same six bits, $010101$, with no bits left over in any reading.

(b) Which direction

$01$ is a prefix of $0101$ — the first two characters of B's codeword are exactly A's entire codeword. The reverse can't hold: a length-4 string can never be a prefix of a length-2 string.

(c) What greedy matching needs

The accumulated bits must reach a state that matches exactly one codeword and cannot also be a strict prefix of some other, longer codeword still in the table. Prefix-freeness is precisely the guarantee that this never happens: the moment your running prefix equals some codeword, no other codeword extends it, so stopping there is always correct. Break that guarantee — as $A{=}01,B{=}0101$ does — and a decoder has no principled way to choose between stopping at $01$ (reading $A$) or reading on toward $0101$ (reading $B$); both are locally consistent with what it's seen so far.

Why this matters: this is the exact property B2's decoder leans on with no further checking — one linear pass, stop the instant the running prefix matches a table entry. It's only safe because Problem B's input is guaranteed prefix-free.

(a) Implementation 
def decode(table, bits):
    rev = {v: k for k, v in table.items()}
    out, cur = [], ''
    for b in bits:
        cur += b
        if cur in rev:
            out.append(rev[cur]); cur = ''
    if cur:
        raise ValueError(f"leftover undecodable bits: {cur}")
    return ''.join(out)

if __name__ == "__main__":
    k = int(input())
    table = {}
    for _ in range(k):
        sym, code = input().split('\t')
        table[sym] = code
    bits = input()
    print(decode(table, bits))

No. B2's loop only ever asks "is the accumulated prefix, cur, an exact key in the table?" — nothing in that check, or anywhere else in the function, refers to frequencies or to how the table was built. Decoding correctness depends only on the table being prefix-free; optimality never enters.

Huffman on $a{:}2,b{:}1,c{:}1,d{:}1$ (total weight 5) merges the three weight-1 leaves down in a way that leaves every symbol at depth 2: $b{=}00,c{=}01,d{=}10,a{=}11$, cost $5\times2=10$.

Sample 3's table costs $2(1)+1(2)+1(3)+1(3) = 2+2+3+3=10$ — the same 10. Relabelling the identical codeword set backwards — $d{=}0,c{=}10,b{=}110,a{=}111$, shortest word now on the rarest symbol — costs $2(3)+1(3)+1(2)+1(1)=6+3+2+1=12$.

So: sample 3's table happens to tie the true optimum here, purely because it (like the real Huffman table) put its shortest word on the most-frequent symbol. The backwards relabelling — still prefix-free, same four codewords, same decoder, no bug anywhere — proves "valid" and "optimal" are genuinely different properties: it costs 2 bits more on the same input. Why this matters: A5 and C6 show two different Huffman-optimal tables can tie on total cost; this question shows a non-Huffman table can also tie, or can lose — prefix-freeness guarantees decodability, never cost.

B4prove

Cost the decoder from B2.

  1. Argue that decoding runs in $O(M)$ time, where $M$ is the length of the bitstring — one pass, each bit examined once. Contrast this with a naive decoder that, at every bit position, tries matching all $k$ table entries from scratch; give its complexity and say exactly what work the $O(M)$ version avoids repeating.
  2. Does the number of decoded characters, or the alphabet size $k$, appear anywhere in your $O(M)$ bound? Explain why each does or doesn't.
(a) One pass versus brute force

B2's loop extends the running prefix by one bit and does a single $O(1)$ hash-map lookup, then moves on — every bit is touched exactly once, so decoding is $\Theta(M)$, full stop. A naive decoder that instead tries all $k$ codewords against the remaining bits at every position pays $O(k)$ work per position it's tried at, giving roughly $O(Mk)$ in the worst case.

The wasted work is re-deriving, from scratch at every position, a fact a hash lookup already gives for free: "is this exact prefix a known codeword." The one-pass version remembers only the running prefix and throws it away the instant it resolves; it never re-examines bits it has already committed to a decoded symbol.

(b) What does and doesn't appear

The output length doesn't need a separate term because it's already implied by $M$: every codeword has length $\ge 1$, so the number of decoded characters is at most $M$, and that work is folded into the single pass already counted.

$k$ doesn't appear in the per-bit cost because the hash-map lookup is $O(1)$ regardless of how many entries the table holds. Building that hash map from the $k$ input lines costs $O(k)$ once, up front — separate from, and dominated by, $O(M)$ for any message actually worth encoding, i.e. whenever $M \ge k$.

B5compute

Real bitstreams aren't always well-formed. Extend B2 to handle two distinct failure modes.

  1. The bitstring ends with bits that never complete into any codeword. How does B2's implementation already detect this, and what should it do about it?
  2. A different failure: partway through, the running prefix becomes a string that is not a prefix of any codeword in the table — no future bit could ever complete it. Can this be detected earlier than waiting for the whole stream to end, and would you want it to be?
(a) Leftover bits at the end

B2's loop already leaves this visible for free: if the stream is malformed this way, cur is non-empty once the loop finishes, since nothing forces it to empty out. The if cur: raise ValueError(...) after the loop turns that leftover state directly into a reported failure rather than silently dropping the trailing bits.

(b) A dead prefix, detected early

Yes — but not with a plain hash map of complete codewords, which can only ever say "match" or "not yet, keep reading," never "this can never match." Detecting a dead end early needs a structure that can answer "does any codeword start with this prefix," not just "is this prefix itself a codeword" — a trie built from the table does this in $O(1)$ per step, since a dead prefix simply has no corresponding node to descend into.

Whether you want this depends on what you're building. For an offline decoder reading a complete file, catching a dead prefix at bit 5 instead of bit 5000 mainly makes error messages more useful, since the whole stream is available either way. For anything reading a live stream — decoding as bits arrive rather than after the fact — early detection is the only way to fail fast at all, since there may be no "end of stream" moment to fall back on.

Part C · Optimal

7 questions · ~85 min

C1prove

Two claims sit underneath everything else in this part.

  1. In an optimal code tree — one achieving the minimum possible total weighted path length for its symbol set — prove that no node has exactly one child.
  2. Using (a), prove the sibling property (slide 20): the sibling of a deepest leaf is itself a leaf, at that same maximum depth.
(a) No one-child nodes, by contradiction

Suppose an optimal tree $T$ has some internal node $v$ with exactly one child $c$. Delete $v$ and attach $c$ directly to $v$'s former parent (or make $c$ the new root, if $v$ was the root). Every leaf in $c$'s subtree now sits exactly one level shallower than before; every other leaf in the tree is untouched.

Total cost is $\sum_{\text{leaf}} \text{freq}\times\text{depth}$, and at least one leaf (in $c$'s subtree, which is non-empty) just had its depth reduced by exactly 1 while every other term stayed fixed. This is exactly where every symbol having strictly positive frequency is used: a positive-weight term getting strictly smaller means the sum strictly decreases. That contradicts $T$'s optimality. So no such $v$ exists — every internal node has exactly two children.

(b) The sibling property

Let $\ell$ be a leaf at the tree's maximum depth $D$. By (a) the tree is full, so $\ell$'s parent has exactly two children: $\ell$ and a sibling $s$. Suppose $s$ is not a leaf. Then by (a) again, $s$ has two children, so $s$ has some descendant leaf $\ell'$ strictly deeper than $s$ itself — and since $s$ sits at depth $D$ (siblings share a depth), $\ell'$ is at depth $\gt D$.

That contradicts $D$ being the maximum depth in the tree — the hypothesis this whole argument turns on. So $s$ must be a leaf, and since it's $\ell$'s sibling it shares $\ell$'s depth $D$: $s$ is a deepest leaf too. $\blacksquare$

C2prove

Prove CLRS Lemma 15.2 (slide 21): if $x,y$ are two symbols of minimum frequency in the alphabet, there is an optimal tree in which $x$ and $y$ are siblings at maximum depth.

Work out the change in total cost from swapping two leaves' positions as a single product: (frequency difference) $\times$ (depth difference). Then pin down the sign of each factor separately for the specific swap you need — don't try to reason about the sign of the product directly.

Set-up

Let $T$ be any optimal tree. By C1, $T$ has two leaves $a,b$ that are siblings at the maximum depth $D$. If $x=a$ and $y=b$ (in either order) there's nothing to prove, so assume not.

The cost of a single swap

Swapping the positions of any two leaves $u$ (frequency $f_u$, depth $d_u$) and $v$ (frequency $f_v$, depth $d_v$) — every other leaf untouched — changes total cost by $$\Delta = \big(f_u d_v + f_v d_u\big) - \big(f_u d_u + f_v d_v\big) = (f_u-f_v)(d_v-d_u).$$

Applying it twice

Swap $x$ into $a$'s position. Here $u=x,\ v=a$: $\Delta_1=(f_x-f_a)(d_a-d_x)$. Since $x$ has minimum frequency over the whole alphabet, $f_x\le f_a$, so $f_x-f_a\le 0$. Since $D$ is the maximum depth and $d_a=D$, $d_a-d_x = D-d_x\ge 0$. A non-positive factor times a non-negative factor is non-positive: $\Delta_1\le 0$.

Now swap $y$ into $b$'s position (in the tree that resulted from the first swap). The identical argument applies with $u=y,\ v=b$: $f_y\le f_b$ gives $\Delta_2\le 0$.

Conclusion

Let $T_2$ be the tree after both swaps: $\text{cost}(T_2) = \text{cost}(T) + \Delta_1+\Delta_2 \le \text{cost}(T)$. But $T$ was optimal, so nothing can cost less: $\text{cost}(T_2)\ge\text{cost}(T)$ too. Hence $\text{cost}(T_2)=\text{cost}(T)$ — $T_2$ is also optimal — and in $T_2$, $x$ and $y$ sit exactly where $a,b$ did: siblings, at depth $D$. $\blacksquare$

Independent check: if $x=a$ already, $f_x-f_a=0$ and $\Delta_1=0$ automatically — the formula degenerates correctly rather than needing a separate case. ✓

Using C2's swap-cost formula, explain in general terms what this specific trade is buying and what it's spending.
  2. Forcing the first merge to instead combine $s(5)$ with $t(5)$ — neither one a minimum-frequency symbol — verifiably still lands on the optimal 94. Does this contradict C2? What does the contrast between (a) and (b) tell you about what a greedy-choice property actually guarantees?
(a) What the bad trade buys and spends

Net change: $h$'s $-2$ bits (freq 1, so cost $-2$) plus $n$'s $-1$ bit (freq 1, cost $-1$) against space's $+1$ bit (freq 5, cost $+5$): $-2-1+5=+2$, exactly the 96-vs-94 gap.

Pairing $h$ with $s$ instead of with $n$ lets $h$ — and, knock-on, $n$ — sit shallower than the optimum needs. That looks like a win, but frequency-1 symbols are cheap to leave deep in the first place: an extra bit of depth on a frequency-1 leaf only costs 1. What the trade actually spends is $s$'s rightful position — using $s$ up on an early merge with $h$ leaves some other weight-5 symbol (here, space) to absorb the depth $s$ would otherwise have taken, and a weight-5 symbol getting one bit deeper costs 5, not 1. This is precisely the trade C2's swap argument rules out: paying a high-frequency symbol's bit-cost to buy a low-frequency symbol something it didn't need.

(b) One-directional, not two-directional

No contradiction. C2 proves merging the two minimum-frequency symbols is always safe — it does not claim every other pairing is always unsafe. $(s,t)$ happens to still route to an optimal tree; $(h,s)$ provably doesn't. Nothing in C2 tells you in advance which non-minimal pairings are secretly fine and which aren't — working that out would need re-running an exchange argument for that specific pairing, on that specific frequency table, from scratch.

Why this matters: a greedy-choice property is a guarantee about one choice, not a verdict on every alternative. "This is safe" is a far weaker, far more useful claim than "everything else fails" — and it's the only kind of claim C2 actually makes. The two smallest is the one pairing you don't have to re-derive a proof for, every single time.

C4prove

Prove CLRS Lemma 15.3 (slides 22–23). Let $T$ be an optimal tree for alphabet $S=\{x,y\}\cup R$ with $x,y$ as siblings at depth $D$ (C2 guarantees such a $T$ exists). Let $T'$ be $T$ with $x,y$ deleted and their shared parent turned into a single leaf $z$, weight $f_z=f_x+f_y$, on the reduced alphabet $S'=\{z\}\cup R$. Show: $T'$ is optimal for $S'$, and every optimal tree for $S'$ expands back (re-splitting $z$ into $x,y$) into an optimal tree for $S$.

Don't try to prove "$T$ optimal for $S$ iff $T'$ optimal for $S'$" for an arbitrary pair. Fix the one $T$ from C2 and its $T'$, derive the exact cost identity between them, then argue by cut-and-paste in each direction: assume a better competitor exists on one side, build its counterpart on the other side, and show it would have been a better competitor there too.

The cost identity

Every symbol in $R$ has the same depth in $T$ and $T'$ (nothing about their positions changed). So $$\text{cost}(T) = \sum_{w\in R} f_w\,\text{depth}(w) + f_x D + f_y D, \qquad \text{cost}(T') = \sum_{w\in R} f_w\,\text{depth}(w) + f_z(D-1).$$ Since $f_z=f_x+f_y$, the first sums agree and $f_xD+f_yD - f_z(D-1) = f_z\cdot D - f_z\cdot D + f_z = f_z$. So $$\text{cost}(T) = \text{cost}(T') + f_x + f_y.$$ This holds for any tree with $x,y$ as siblings, paired with its $z$-reduction — it's an identity about the shape, not something special to an optimal $T$.

$T'$ is optimal for $S'$

Suppose not: some tree $V'$ on $S'$ has $\text{cost}(V') \lt \text{cost}(T')$. Un-merge $V'$ — split $z$'s leaf back into an internal node with children $x,y$ — to get a tree $V$ on $S$, with $x,y$ siblings by construction. The identity applies to $(V,V')$ too: $\text{cost}(V)=\text{cost}(V')+f_x+f_y \lt \text{cost}(T')+f_x+f_y = \text{cost}(T)$. But $T$ was optimal for $S$ — nothing beats it. Contradiction, so no such $V'$ exists: $T'$ is optimal.

Optimal subproblem solutions expand back to optimal solutions

Let $O'$ be any optimal tree for $S'$. Since $T'$ is also optimal (just shown), and all optimal trees for the same alphabet share the same cost, $\text{cost}(O')=\text{cost}(T')$. Un-merge $O'$ into $O$ on $S$: by the identity, $\text{cost}(O) = \text{cost}(O')+f_x+f_y = \text{cost}(T')+f_x+f_y = \text{cost}(T)$. $O$ costs exactly what the optimal $T$ costs, so $O$ is optimal too. $\blacksquare$

Why this matters: this is what actually licenses recursion. It's not enough that some good tree exists for the smaller alphabet — every step needs "solve the subproblem optimally, un-merge, get an optimal answer to the original," which is exactly the two directions just proved, not one.

C5recall

Name the two properties C2 and C4 each establish, in the general sense used across every greedy-algorithm correctness proof — not just this one — and say why the algorithm needs both, not just one.

The two properties

Greedy-choice property (C2): a globally optimal solution can always be reached by making the locally best choice first — merge the two lowest-frequency symbols — without ever needing to revisit that choice later. Optimal substructure (C4): an optimal solution to the full problem contains an optimal solution to the smaller subproblem left behind after the greedy choice, and conversely.

Why both, and neither alone

Greedy-choice alone says it's safe to merge the two smallest first, but says nothing about what to do with what's left — without optimal substructure there's no guarantee that solving the remaining, smaller problem well combines into a good solution overall. Optimal substructure alone, without greedy-choice, only says that recursion behaves well if you happen to start from the right first move — it never tells you which first move that is, which would force trying all $\binom{n}{2}$ possible first pairings to find out.

Together they license exactly the one-pass algorithm on slide 6: make the greedy choice once, recurse on what's left, never backtrack.

C6prove

A5 showed, by example, that the lecture's tree and a natural from-scratch implementation disagree on which of $s,t,e,\text{space}$ — all frequency 5 — gets the 2-bit code, while both total 94. Prove this had to be possible: use C2's own proof to show exactly where it stops distinguishing between tied symbols.

Re-examine where C2's proof actually uses the values $f_x,f_y$: only through the inequalities $f_x\le f_a$ and $f_y\le f_b$, comparing against whatever sits at maximum depth. Nothing in that step distinguishes between two symbols with equal frequency — if $f_x=f_{x'}$, the inequality $f_x\le f_a$ holds if and only if $f_{x'}\le f_a$ does too, since they're the same number. The proof goes through identically whichever of $x,x'$ you send to the deepest position.

Concretely: C2 only pins down that some frequency-5 symbol ends up paired with frequency-4 $r$ at the point a weight-9 merge happens — the lecture's construction sends space there, a first-occurrence-ordered implementation sends $s$. The proof's only appeal to $x,y$'s identity is an inequality, and inequalities between tied values don't distinguish which tied value satisfies them — so both choices, and any other respecting the same merge weights, are left equally valid.

What C4's identity does pin down exactly, not up to ties: total cost. That identity is stated purely in terms of frequencies — $\text{cost}(T)=\text{cost}(T')+f_x+f_y$ — and never refers to which specific tied symbol occupies which position, so it forces the same number regardless.

Why this matters: this is the general reason Huffman codes aren't unique but Huffman costs are. It isn't a quirk of this string — it's built into exactly where the optimality proof does, and doesn't, look at frequency values.

C7prove

The algorithm (slide 6) starts with one leaf per symbol and merges until one tree remains. Walk it through on an alphabet of size 1.

  1. With exactly one symbol, how many merges does the procedure perform, and what is "the tree" at the end?
  2. A3(c) showed real implementations give this symbol a 1-bit code by convention, even though $\lg 1=0$. Prove that no valid prefix-free code can give a 2-symbol alphabet less than 1 bit each — that's A1(d)'s argument — then show precisely why that same argument does not apply once you're down to exactly one symbol, and what does step in instead.
(a) Zero merges

With one symbol, the algorithm already has exactly one tree — a single leaf — before it does anything, so "repeat until one tree remains" is satisfied immediately: zero merges. That leaf has no edges leading to it from anywhere; its root-to-leaf path has length 0.

(b) Why A1(d)'s argument is silent here

A1(d)'s argument needs a second codeword for the empty string to be a prefix of — a 0-bit codeword is banned because it would be a prefix of every other, nonempty codeword sharing its table, which is exactly what breaks unambiguous left-to-right decoding. With only one symbol in the whole alphabet, there is no second codeword for the empty string to conflict with — a one-entry table $\{\text{symbol}\to\varepsilon\}$ is, formally, vacuously prefix-free. A1(d)'s argument doesn't rule out 0 bits here; it can't, because the condition it depends on — something else in the table for the empty word to be a prefix of — is exactly what's missing.

The actual obstruction is a different one, already identified in A3(c): a 0-bit code carries no way to recover how many times the symbol occurred, since the encoded bitstream is the empty string whether the source had one occurrence or a million. That's a statement about recovering the message's length, not about ambiguity between distinct codewords. The single-symbol case is exactly where those two concerns — usually bundled together under "prefix-free" — come apart.

D2prove

Part B's decoder needs the exact table Part A's encoder used. For a real message, that table has to be sent or stored too — it isn't free.

  1. Order-of-magnitude only: for an alphabet of $n$ symbols, roughly how many bits does transmitting the table itself cost, storing each symbol plus its codeword directly?
  2. Using sample 1 as a reference ($n{=}9$, Huffman saves $124-94=30$ bits over fixed-length): sketch, roughly, why a short-enough message could make the table cost more than encoding saves — and name one real technique that reduces this overhead.
(a) Rough table cost

Each entry needs the symbol itself (a fixed cost — 8 bits for a byte alphabet) plus its codeword, which is at most on the order of $n$ bits in a maximally skewed tree and typically closer to $\lg n$-ish for a balanced one. That puts the whole table somewhere around $O(n\log n)$ bits for a reasonably balanced tree, growing toward $O(n^2)$ in a pathological one. For sample 1's $n=9$ with codeword lengths up to 5 bits: roughly $9\times(8+4) \approx 108$ bits just to write the table down plainly — already more than the 30 bits the encoding saved.

(b) When the overhead wins

Savings scale with message length $N$ — roughly $N\times(\text{fixed bits/char} - \text{Huffman avg bits/char})$ — while the table's cost is fixed by the alphabet, independent of $N$. For a short enough message the fixed table cost simply doesn't have enough $N$ to be amortised against, and the "saving" goes negative overall once you count what the decoder actually needs to receive.

One real fix: transmit only codeword lengths (each $O(\log(\text{max length}))$ bits) rather than full codewords, and reconstruct the actual bit patterns canonically from the lengths and a fixed symbol ordering — this is exactly what canonical Huffman codes do (D4 names the general family). It shrinks the table without touching anything about how well the codewords themselves compress the message.

Which of these code tables could have come out of Huffman's algorithm, for some set of frequencies — and which definitely could not?

  1. $\{a{:}0,\ b{:}10,\ c{:}11\}$

  4. $\{a{:}0,\ b{:}10,\ c{:}110,\ d{:}1111\}$

1 — valid

The standard 3-leaf shape: one symbol at depth 1, two siblings at depth 2. Achievable for, e.g., $a{:}2,b{:}1,c{:}1$.

2 — invalid, not even prefix-free

$b{=}1$ is a prefix of $c{=}11$: this fails the basic decodability requirement before optimality is even a question. A message starting $11\ldots$ can't be told apart between "$b$ then something" and "$c$".

3 — valid

Lengths $2,2,2,3,3$. The two length-3 codewords, $d{=}110$ and $e{=}111$, share the prefix $11$ and differ only in the last bit — genuine siblings, satisfying C1b. Achievable for a frequency set with $d,e$ the two smallest and roughly equal, $a,b,c$ larger.

4 — invalid, but for a different reason than 2

This one is prefix-free — check every pair and none is a prefix of another. The problem is structural: $d{=}1111$ is the only codeword starting $111$, which means the node at prefix $111$ has exactly one child. C1(a) already rules this out for any optimal tree — if these were real frequencies, shortening $d$ to $111$ would strictly reduce cost, so no optimal (Huffman) construction would ever leave it at 4 bits with an empty sibling slot. Valid prefix-free code; not a Huffman output.

5 — valid

This is exactly A2's own answer, verified there: $a{=}0,c{=}100,b{=}101,d{=}111,f{=}1100,e{=}1101$, achieved by the frequencies $a{:}45,b{:}13,c{:}12,d{:}16,e{:}9,f{:}5$.

Two different flaws, both real: (2) fails to be a valid code at all; (4) is a perfectly valid code that simply isn't optimal. "Prefix-free" and "Huffman-optimal" are different bars, and a table can clear the first without clearing the second — B3 already made the same point from the decoding side.

D4recall

Slide 24 closes by saying Huffman is optimal "for the alphabet with given frequencies," but beating it needs "an encoding that can encode multiple symbols at once."

  1. What does the optimality proof (C1–C4) implicitly assume about how symbols get encoded, that a multi-symbol scheme would break?
  2. Name one real situation where frequencies aren't known upfront — unlike every problem on this sheet — and say, in one sentence, what would have to change about Problem A to handle it.
(a) The hidden assumption

C1–C4 prove optimality within the rule "each symbol, independently, gets its own whole-number-of-bits codeword." A symbol with probability $0.9$ carries only about $0.15$ bits of information ideally, but no prefix code can give it less than 1 bit — Huffman's proof is airtight about being the best possible under that one-symbol-one-codeword constraint, and says nothing about schemes that don't play by it: encoding pairs or blocks of symbols together, or genuinely fractional-bit allocation, as arithmetic/range coding does. Huffman can still be optimal in its own lane and be beaten by a scheme in a different lane.

(b) When frequencies aren't known in advance

Streaming or live text compression, where the encoder has to start before it has seen the whole input. Problem A would need to change from "read the whole line, then decide" to something that updates its code as data arrives — either two passes (count first, ship the table, then encode) or a genuinely adaptive scheme where encoder and decoder maintain synchronised statistics and neither ever transmits a table at all.
